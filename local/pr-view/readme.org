#+TITLE: pr-view

Bitbucket Cloud *and* GitHub pull requests inside an Emacs xwidget.
Elisp owns HTTP and tokens; =ui/= only renders.  List (Open / Draft /
Merged / Declined), description, unified diff, commits, reviewer
approvals, create, approve, merge.

* Status

| Item    | Value |
|---------+-------|
| Package | =local/pr-view/= |
| Entry   | =M-x pr-view= · =SPC g p= · alias =M-x bitbucket-pr= |
| Needs   | GUI Emacs with xwidgets |

* Try it

1. GUI Emacs built with xwidgets (this config's emacs-plus@31 is).
2. Put credentials in =~/.authinfo.gpg= (or env vars below).
3. Open a file in a GitHub or Bitbucket repo and run =M-x pr-view=
   (or =SPC g p= after tangle/reload).
4. Click a row for description + diff; ← List / Esc goes back.
5. =M-x pr-view-open-in-browser= opens the last PR on the forge.

Force a forge: =M-x pr-view-github= / =M-x pr-view-bitbucket=.

After editing this package, drop straight's build cache and restart:

#+begin_src emacs-lisp :tangle no
  (delete-directory (expand-file-name "straight/build/pr-view" user-emacs-directory) t)
#+end_src

* Auth

GitHub (first match wins):

- =GITHUB_TOKEN=
- auth-source host =api.github.com=
- =gh auth token=

Token scopes: =repo= (private) or public read; fine-grained needs
Pull requests: Read and Write (create / approve / merge).

Bitbucket Cloud (API token; App passwords are gone):

- =BITBUCKET_TOKEN= (same as the bitbucket-pr-manager skill)
- auth-source host =api.bitbucket.org= (password = API token)
- optional =BITBUCKET_USER= / =pr-view-bitbucket-username= = Atlassian email, only to pick the auth-source line

Create the token at Atlassian account → API tokens with scopes.  Requests use
=Authorization: Bearer <token>= (email is not sent).  Scopes for v0.1:

- =read:repository:bitbucket=
- =read:pullrequest:bitbucket=
- =write:pullrequest:bitbucket= (create / approve / merge)

~/.authinfo.gpg example:

#+begin_example
machine api.github.com password ghp_...
machine api.bitbucket.org login you@example.com password ATATT3xFfGF0...
#+end_example

Workspace/repo default from =origin=. Override with
=pr-view-github-owner= / =pr-view-github-repo= or
=pr-view-bitbucket-workspace= / =pr-view-bitbucket-repo=.

* Merge conflicts

The =Merge= button asks for confirmation *in the page*. It used to call
=window.confirm=, which inside xwidget's WebKit returns =false=
immediately without drawing anything --- so the click was cancelled in
silence and Merge had never worked at all. Comment deletion had the same
guard and the same problem.

Conflicts show up before you click, as a banner listing the files, a
=⚠ Conflicts n= chip, a =⚠= on the Files changed tab, and a
=Conflicted= badge per file. Each forge says it differently:

- GitHub: =mergeable_state= is =dirty= on a conflicted PR. No file list.
  (=mergeable= itself is a JSON boolean, and this parser maps =false=
  and =null= alike to nil --- reading *that* field is how the old check
  managed to be true always.)
- Bitbucket: =GET /pullrequests/{id}/conflicts=, which answers per file
  with a sentence --- =frontend/public/releases.json — File modified in
  both source and destination=. Neither the pull request nor =diffstat=
  carries this: diffstat's =status= enum is only
  added/removed/modified/renamed, and a conflicted file comes back
  =modified=.

There is deliberately no pre-flight merge call. Bitbucket's merge
endpoint takes no =dry_run= --- its published spec lists only =async= ---
so asking whether a merge would work would *be* the merge. A refused
merge still paints the banner, as a backstop: the forge is the only
authority on whether a merge is actually allowed.

API errors now show the forge's own sentence (=error.message= on
Bitbucket, =message= on GitHub) rather than 180 characters of raw JSON.

* Reviewer approvals

Each reviewer chip carries its verdict -- ✓ approved (green),
✘ changes requested (red), · still waiting -- with an =n/m approved=
count in front.  The two forges keep that verdict in different places:

- Bitbucket: in =participants=, never in =reviewers=.  It rides along
  with the PR, so the chips are right on first paint.
- GitHub: in =/pulls/{id}/reviews=, and a reviewer is *dropped* from
  =requested_reviewers= the moment they review.  pr-view fetches the
  reviews separately and adds those people back, so an approval is
  visible at all; the chips settle a moment after the view opens.

* ClickUp tasks

With =clickup-view= installed, the detail view has a ClickUp row: the
tasks the PR cites, each with its status and name.  A click opens the
task in clickup-view, where it can be read, moved or commented on; a
ClickUp task link in the description or a comment does the same.
Without clickup-view the row never appears.

- Found in the title, the source branch, the description, then the
  commits as they arrive (a task keeps the first place it was seen;
  the tooltip says which).  The rule is clickup-view's own
  =clickup-view-task-refs=: a task link or =CU-<id>=, and an id has a
  digit, so =CU-ids= in prose is not a task.
- Each task is one =GET /task/{id}= through =clickup-view-task-brief=,
  for at most 20 a PR: ClickUp allows 100 requests a minute on most
  plans, and a release PR can cite dozens.  The rest show their id.
- Six chips show; =+N more= shows the rest.  A task that cannot be read
  (another workspace, no token) keeps its id, dashed, with the reason
  in the tooltip.  Closed tasks are muted.
- When clickup-view cannot open a task (no token, no xwidgets, a custom
  id) the browser gets it.
- Lookups and commits arrive late; the page drops any meant for a PR
  that is no longer open, and patches the row in place so a comment
  being typed survives.

Every intent the page sends now carries a counter =n=.  =xwapp= ignores
a title identical to the last one it read, so clicking the same chip
twice --- or Refresh twice --- used to do nothing the second time.

* The page

=ui/= runs on xwapp's page kit (=../../xwapp/ui/=, see xwapp's
README): the shared colours, and the intent bridge, which queues
intents and counts them.  Before it, two clicks within one poll lost
the first, and a second identical one (Refresh twice) was taken for
the one already read.  The page carries a Content-Security-Policy ---
no inline script or handler, no fetch, images https or data: --- so an
avatar that fails to load is dropped by a listener, not an =onerror=
attribute.

* On your phone

From the herd page on your phone, a PR chip opens pr-view's page there
--- through xwapp's address without the secret,
=/open/pr-view#pr=<the PR's address>=, the Bitbucket or GitHub token
staying in Emacs.  The page says which pull request it is for once it
loads (=ready= with =pr=); a repository's list keeps its place the
same way (=repo=, =KIND/OWNER/REPO=).  Only github.com and
bitbucket.org pull requests, owner and repository in the forges' own
characters.  The address follows the page as it moves, so a reload,
or Emacs restarted (=pr-view-reopen=), comes back to the same place.

There, Open and a commit open on the forge in a tab of the phone, Copy
copies to its clipboard, and a ClickUp task opens in clickup-view's
page there; Create, which takes a branch of a checkout on the Mac, is
not offered.  Under 640 points the bar is one line, its buttons their
first word, and a list row's when, comments and reviewers one line
under its title; to a finger, controls 32 points and more, form text
16px.

In any narrow window --- the phone, or Emacs split side by side ---
nothing scrolls sideways but a block of code or a wide table, each by
itself: a long link, path or branch breaks rather than widen the page.
Under 720 points a commit is a card, who, which and when on a line and
its message under them.

Narrow or short --- under 720 points across or 560 down, a phone on
its side included --- a pull request scrolls as one page, its tabs held
at the top: held still, its head left a phone a quarter of the screen
to read in.  A tab picked once its head has scrolled away opens at its
start, under the tabs.  At the desk the head stays and the tab scrolls
under it, as before.

* A checkout's uncommitted changes

=M-x pr-view-changes= shows what the checkout at hand has not
committed in a pull request's file view: against =HEAD=, staged or
not, a file git does not track yet as a new one --- whole, or named
with why it is not shown: binary, larger than 128k, not a plain file
(a link is not followed out of the checkout).  Files git ignores are
left out.  Up to fifty new files and two megabytes of diff; past them
the files left out are counted.  git runs apart from Emacs, for twenty
seconds at most, its diff drivers and textconv filters not run.
Refresh reads it again; Back is to the repository's pull requests,
when it is on a forge.

From the herd page --- a checkout's =N uncommitted= chip --- it opens
on the phone at =/open/pr-view#local=<root>=.  An address names any
directory, so the page shows only a checkout opened here with
=pr-view-changes=, or one a function on
=pr-view-local-allowed-functions= vouches for --- ghostherd's: the
checkouts the herd is in --- and refuses the rest, running no git
there.

** A review of them

When a function on =pr-view-local-recipients-functions= says someone
may be sent a review of the checkout --- ghostherd: the agents working
in it --- a line picked takes a comment, in a box under it: Add, or
=⌘↩=; Escape puts away one with nothing new in it.  A comment left for
another line, another file, Refresh or Send goes in as written.  Each
stays under its line, its file counting them in the tree; one whose
line has moved since --- the same number on the same side, with the
same text, is no longer there --- waits at the head of its file, with
the line it was on.  Text selected in a line is not a line picked.

They go together, from the bar at the foot: how many (opened, each one,
to go to it or remove it, and a note to send with them), whom to (the
first offered, or the one picked last), Send.  Emacs writes them as one
text --- the checkout and its branch, then each comment numbered at its
file and line (or the line taken out, by its number before), with that
line quoted, then the note --- and hands it to the one picked; the page
says what was done, or why not, and keeps them to send again.  Until
sent they are kept in that browser, per checkout, over a reload; a
private window keeps them as long as the page.

* For other packages

ghostherd's herd page shows the PR an agent's branch is on.  Two
functions serve it, and anything else that wants the same:

- =pr-view-branch-pr= =DIR CALLBACK=: the pull request of the branch
  checked out at =DIR=, asked of =DIR='s own remote (not the
  =pr-view-github-*= / =pr-view-bitbucket-*= repository).  An open PR
  before a closed one, then the newest; with the ClickUp tasks its
  title, branch and description cite when clickup-view is there.
  =nil= on the default branch, a detached head, a repository on no
  forge, or a branch with no PR; =((error . TEXT))= when the forge
  could not be read.  Nothing goes to pr-view's page.
- =pr-view-pr-brief= =DIR ID CALLBACK=: pull request =ID= of =DIR='s
  repository, the same way; =((error . TEXT))= when it cannot be read.
- =pr-view-remote= =DIR=: the forge repository =DIR='s origin is, as
  =(:kind :owner :repo)=.
- =pr-view-open-pr= =DIR ID=: open PR =ID= of =DIR='s repository here,
  its detail rather than the list.
- =pr-view-local-stat= =DIR=: what the checkout =DIR= is in has not
  committed, as the page counts it: =(:root :files :added :deleted)=,
  or =nil= outside a checkout.  Run as asked, not apart.
- =pr-view-changes= =DIR=: open that checkout's changes here.
- =pr-view-local-allowed-functions=: functions of a checkout's root,
  non-nil when the page may show its changes.
- =pr-view-local-recipients-functions=: functions of a checkout's
  root, each a list of who may be sent a review of its changes, as
  =(:id ID :label LABEL :send FN)= --- =FN= called with the review's
  text, returning a sentence saying what it did.  Asked only of a
  checkout the page may show; the first offered first.
