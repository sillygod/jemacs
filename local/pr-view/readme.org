#+TITLE: pr-view

Bitbucket Cloud *and* GitHub pull requests inside an Emacs xwidget.
Elisp owns HTTP and tokens; =ui/= only renders.  List (Open / Draft /
Merged / Declined), description, unified diff, commits, reviewer
approvals, create, approve, merge.

* Status

| Item    | Value |
|---------+-------|
| Package | =local/pr-view/= |
| Entry   | =M-x pr-view= · =SPC g p= · alias =M-x bitbucket-pr= |
| Needs   | GUI Emacs with xwidgets |

* Try it

1. GUI Emacs built with xwidgets (this config's emacs-plus@31 is).
2. Put credentials in =~/.authinfo.gpg= (or env vars below).
3. Open a file in a GitHub or Bitbucket repo and run =M-x pr-view=
   (or =SPC g p= after tangle/reload).
4. Click a row for description + diff; ← List / Esc goes back.
5. =M-x pr-view-open-in-browser= opens the last PR on the forge.

Force a forge: =M-x pr-view-github= / =M-x pr-view-bitbucket=.

After editing this package, drop straight's build cache and restart:

#+begin_src emacs-lisp :tangle no
  (delete-directory (expand-file-name "straight/build/pr-view" user-emacs-directory) t)
#+end_src

* Auth

GitHub (first match wins):

- =GITHUB_TOKEN=
- auth-source host =api.github.com=
- =gh auth token=

Token scopes: =repo= (private) or public read; fine-grained needs
Pull requests: Read and Write (create / approve / merge).

Bitbucket Cloud (API token; App passwords are gone):

- =BITBUCKET_TOKEN= (same as the bitbucket-pr-manager skill)
- auth-source host =api.bitbucket.org= (password = API token)
- optional =BITBUCKET_USER= / =pr-view-bitbucket-username= = Atlassian email, only to pick the auth-source line

Create the token at Atlassian account → API tokens with scopes.  Requests use
=Authorization: Bearer <token>= (email is not sent).  Scopes for v0.1:

- =read:repository:bitbucket=
- =read:pullrequest:bitbucket=
- =write:pullrequest:bitbucket= (create / approve / merge)

~/.authinfo.gpg example:

#+begin_example
machine api.github.com password ghp_...
machine api.bitbucket.org login you@example.com password ATATT3xFfGF0...
#+end_example

Workspace/repo default from =origin=. Override with
=pr-view-github-owner= / =pr-view-github-repo= or
=pr-view-bitbucket-workspace= / =pr-view-bitbucket-repo=.

* Merge conflicts

The =Merge= button asks for confirmation *in the page*. It used to call
=window.confirm=, which inside xwidget's WebKit returns =false=
immediately without drawing anything --- so the click was cancelled in
silence and Merge had never worked at all. Comment deletion had the same
guard and the same problem.

Conflicts show up before you click, as a banner listing the files, a
=⚠ Conflicts n= chip, a =⚠= on the Files changed tab, and a
=Conflicted= badge per file. Each forge says it differently:

- GitHub: =mergeable_state= is =dirty= on a conflicted PR. No file list.
  (=mergeable= itself is a JSON boolean, and this parser maps =false=
  and =null= alike to nil --- reading *that* field is how the old check
  managed to be true always.)
- Bitbucket: =GET /pullrequests/{id}/conflicts=, which answers per file
  with a sentence --- =frontend/public/releases.json — File modified in
  both source and destination=. Neither the pull request nor =diffstat=
  carries this: diffstat's =status= enum is only
  added/removed/modified/renamed, and a conflicted file comes back
  =modified=.

There is deliberately no pre-flight merge call. Bitbucket's merge
endpoint takes no =dry_run= --- its published spec lists only =async= ---
so asking whether a merge would work would *be* the merge. A refused
merge still paints the banner, as a backstop: the forge is the only
authority on whether a merge is actually allowed.

API errors now show the forge's own sentence (=error.message= on
Bitbucket, =message= on GitHub) rather than 180 characters of raw JSON.

* Reviewer approvals

Each reviewer chip carries its verdict -- ✓ approved (green),
✘ changes requested (red), · still waiting -- with an =n/m approved=
count in front.  The two forges keep that verdict in different places:

- Bitbucket: in =participants=, never in =reviewers=.  It rides along
  with the PR, so the chips are right on first paint.
- GitHub: in =/pulls/{id}/reviews=, and a reviewer is *dropped* from
  =requested_reviewers= the moment they review.  pr-view fetches the
  reviews separately and adds those people back, so an approval is
  visible at all; the chips settle a moment after the view opens.
