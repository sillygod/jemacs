#+TITLE: xwapp

Plumbing for Elisp-backed pages in an xwidget --- or in a web browser:
a local HTML page renders, Elisp owns HTTP and secrets.  Used by
=pr-view=, =clickup-view= and ghostherd's herd page.

* Shape

- Page → Emacs: the page sets =document.title= to =PREFIX + JSON=; a
  timer polls the title and hands the parsed intent to the app's handler.
  xwidget-webkit gives Emacs no message channel it can listen on.
- Emacs → page: =xwapp-js= calls =NAMESPACE[fn](json)=.
- One =xwapp= struct per app: buffer name, =index.html=, title prefixes,
  JS namespace, idle title, handler, optional on-kill; =xwapp-create=
  takes an optional =:reopen= too (see "A tab that comes back").  The
  struct gains no slot: its layout is compiled into the packages that
  use it, and straight does not rebuild them when xwapp changes.

#+begin_src emacs-lisp :tangle no
  (defvar my-app
    (xwapp-create :buffer-name "*my-app*"
                  :index (expand-file-name "ui/index.html" my-dir)
                  :prefixes '("myapp:")
                  :namespace "APP"
                  :idle-title "My App"
                  :handler #'my-app--handle-intent))

  (xwapp-open my-app)                 ; show the page, start polling
  (xwapp-js my-app "render" payload)  ; APP.render(payload)
#+end_src

Whether the page is open, and whether you could be looking at it,
wherever it is:

| =(xwapp-live-p app)= | open: its xwidget, or a browser tab                    |
| =(xwapp-seen-p app)= | in front of you: a window of a focused, visible frame, |
|                      | or the tab in front of a focused browser window        |
| =(xwapp-reload app)= | load it again where it is (edited =ui/= files)         |

* In a web browser

=M-x xwapp-browse= in an app's buffer moves its page to a tab of the
web browser; with =xwapp-browser= non-nil, =xwapp-open= puts every
page there.  The page and the app are unchanged: =xwapp.js= picks the
channel by the page's URL, =file:= or =http:=, and gives the page the
same =emit=.

Emacs serves the page on 127.0.0.1, at a port of its choosing, under a
secret per app that only the tab knows: =/SECRET/<pkg>/ui/index.html=,
and the kit as =/SECRET/xwapp/ui/…=, as the page reaches it from the
xwidget --- and the files the app serves by name, if any (below).
Nothing else is served, and a request naming another host, or from
another site's page, gets nothing.

| =POST hello=  | the page has loaded: it is the app's page now            |
| =GET next=    | Emacs's calls as a JSON array, held until there are some |
| =POST intent= | one intent; the page sends them one at a time, in order  |
| =GET .files/NAME= | a file the app serves by name (below), if it serves any |

- *Emacs never writes to a tab that has not asked.*  A stream pushed
  to the page would block Emacs in =process-send-string= the moment a
  tab stopped reading --- a frozen background tab, a sleeping window.
  So a =next= is always waiting, and Emacs answers it; held 25s, it is
  answered empty and asked again.
- *One page per app,* as an app has one state in Emacs.  The page that
  said hello last is the app's: the tab before it, or the xwidget, is
  let go --- the tab gets 410 and shows that it moved, the xwidget's
  buffer is killed without its on-kill (the app has moved, not
  closed).  =xwapp-open= in Emacs takes the page back the same way.
- *A tab that stops asking is closed.*  Ten seconds without a =next=
  (the tab closed, or frozen) and the app's on-kill runs.  A reload is
  not a close: its hello comes within the ten.
- *A page opens where you clicked.*  A page opened while an intent
  from a tab is handled --- a PR from the herd page --- opens in the
  browser too, whatever =xwapp-browser= says.  (In a new tab each
  time: a tab Emacs opened is not one it can bring to the front.)
- The tab tells Emacs whether it is visible and focused, for
  =xwapp-seen-p=.  An intent arrives on the next turn, from a timer, as
  the title's does.


** Files an app serves by name

A page shows what Emacs keeps outside it --- ghostherd's, the images an
agent's reply named.  =(xwapp-serve-files app DIR REGEXP)= serves the
page the files in DIR (or a function giving it, asked each time) whose
names REGEXP matches whole, case and all: one segment, a regular file,
not a symlink.  The page has each as =XW.file(NAME)=:

- in a browser, =/SECRET/.files/NAME=: under the page's secret, to whom
  the page is served (here, or one of =xwapp-remote-users= through the
  proxy), and nobody else; GET only.  A name's file never changes, so
  it goes =private, max-age=604800, immutable=.  A dot segment is never
  one of the page's files, so the route takes no name from them.
- in the xwidget, a page of =file:=, as a =file:= URL: Emacs says the
  directory in answer to the page's hello, and the page draws again on
  the =xw-files= event (=XW.file= is "" until then).  Its CSP must have
  =img-src file:= --- and ='self'= for the browser.

Anyone the page is served to can ask for any name: make the names ones
nobody guesses.  Nothing here takes a path.

A file of more than 256 KB (=xwapp--send-aside=) goes from a Lisp
thread of its own.  =process-send-string= returns once the last byte is
in the socket, and a phone on a slow link reads slowly: an 8 MB file to
a reader of 2 MB/s held Emacs 5.4 seconds, a key pressed meanwhile
waiting 4.3 of them; from a thread, which waits on the socket with
Emacs free, the key was taken in 4 ms.  The page itself and its calls
are still sent as before.

** A tab that comes back

A page that is not the app's is answered 410, with why:

| =taken=  | another page is, in a tab or in Emacs: the tab says so, and reloading it takes the app back |
| =free=   | none is, and the app can open again: the tab loads again on its own, and takes it          |
| =closed= | none is, and the app cannot: reloading the tab opens it, or Emacs does                     |

An app can open again when it has =:reopen=: a function that does
what its command does before showing the page, for a tab Emacs did not
open.  Two tabs come back that way:

- *After a restart of Emacs.*  While a tab is the page of such an app,
  its secret and the port are kept in =xwapp-state-file= (yours alone,
  =0600=).  Once Emacs is up, =xwapp-resume= loads the app through its
  =:reopen= --- autoloaded, for that --- and Emacs listens where the tab
  asks.  The tab, which has kept asking ("Emacs is not answering"),
  finds the app free.  A tab that does not come back within a minute
  is not waited for; another Emacs on the port is left alone.
- *After the browser froze it.*  Emacs let it go and closed the app;
  thawed, the tab finds it free.

The tab comes back with a /soft/ hello: one that takes nothing another
page has meanwhile.  A tab that was taken from stays where it is, even
once the app is free --- it was left on purpose.  An app without
=:reopen= keeps no address: after a restart its tab says to open it
again from Emacs.

** From your other devices

The pages can reach a phone or another computer through a proxy on
this machine that knows who is asking: =tailscale serve=.  The proxy
takes the request on your tailnet, passes it on, and names the user of
the device it came from.

#+begin_src emacs-lisp
(setq xwapp-port 48123                      ; fixed, for the browser here
      xwapp-remote-hosts '("box.tail1234.ts.net")
      xwapp-remote-users '("you@example.com"))
#+end_src

The proxy forwards to a *Unix socket*, not to the loopback port, and
Emacs listens on both: the port on 127.0.0.1 for the browser on this
machine, the socket (=xwapp-remote-socket=) for the proxy.

#+begin_src sh
# M-x xwapp-remote-serve-setup gives this with the socket's full path:
tailscale serve --bg --https=443 unix:/Users/you/.emacs.d/xwapp/remote.sock
#+end_src

Then =M-x xwapp-copy-remote-url= copies a page's address there, which
holds its secret, so it is not shown: =https://box.tail1234.ts.net/SECRET/...=.

- *What came through the proxy is told by the socket, not a header.*
  Were the proxy pointed at the loopback port, any program on this
  machine that reaches 127.0.0.1 --- another account, a sandbox ---
  could send the same port a request wearing your tailnet =Host= and
  =Tailscale-User-Login=, and be answered as one of your devices, the
  secret handed over through =/open/= (seen 2026-10-13).  =tailscale
  serve= strips a device's own =Tailscale-User-Login= only on what
  truly passes through it; a request straight to the port never did.
  So the proxy forwards to a socket made yours alone, and only a
  request arriving on it is treated as the proxy's.  The loopback port
  answers this machine's browser and nothing else.  What a header
  cannot forge is the transport.
- *For one of =xwapp-remote-users= only.*  On the socket, =tailscale
  serve= puts the device's user in =Tailscale-User-Login=; a request
  with none --- a tagged device --- or another user's gets 404.  Note
  =tailscale serve= rewrites the =Host= to =localhost= on its way to a
  socket, so the =Host= is no proof and no filter --- the transport
  already is.  =xwapp-remote-hosts= is instead the name your devices
  reach you by, in the address and the QR, and the name the page's
  =Origin= must match (=https://= or =http://= it, case aside): a
  cross-site page on the phone is turned away.  The secret is still
  needed too.
- *The address is kept,* with no tab open and over restarts: an
  address saved on a phone keeps working.  At startup =xwapp-resume=
  loads the apps and Emacs listens on =xwapp-port= --- with remote
  hosts it listens whether or not a page was kept, for the proxy
  cannot ask it to begin.  =M-x xwapp-renew-secret= ends an address
  given out.
- *An address without the secret,* =/open/<pkg>=, sends a browser on
  to that app's page under its secret, for one of
  =xwapp-remote-users= only: one to bookmark, or to pass through a
  chat's servers (=xwapp-remote-open-url=).  The app must be loaded.
- *What this keeps out, and what it does not:* the request's path,
  the two checks, and who gets past them --- anyone signed in to
  Tailscale as you does --- in
  [[file:../ghostherd/docs/phone-access.html][ghostherd/docs/phone-access.html]].
- *Opened there, the page is that device's*, as for any tab: the one
  in Emacs, or in a tab here, lets go of it.
- =xwapp-remote-scheme= is ="https"= by default.  The proxy needs a
  certificate for it --- HTTPS turned on for the tailnet, which puts
  the machine's name in the public certificate logs.  Without one,
  =tailscale serve --http=80= and ="http"=: still encrypted between
  devices by the tailnet, but the browser does not count the page as
  secure, which some of its features need.
- *What you tap acts where you are.*  On another device
  (=XW.elsewhere=) a link Emacs would open in its browser opens there
  instead, =XW.open= in the tap itself (iOS opens no tab a script asks
  for later), and a copy goes with =XW.copy= to that device's clipboard
  rather than to Emacs's.  Over plain http there is no clipboard API; a
  selected textarea and =execCommand= still copy, within the tap.  A
  page of another app opens there through its address without the
  secret, below --- the herd page's PR and task chips open pr-view and
  clickup-view so, in one tab each, used again.
- *An address without the secret*, for a message that passes through
  others' hands --- a chat's server keeps what it carries:
  =xwapp-remote-open-url= gives =/open/<pkg>#fragment=.  Asked there by
  one of =xwapp-remote-users=, Emacs sends the browser on to the page
  under its secret, the fragment kept by the browser.  Not from this
  machine, where any page in the browser could ask it.

A page can also give its address to the phone itself, as a QR code: an
element with =data-xw-phone= is its button for it --- the herd page's
Phone, beside Refresh.

- *Shown only where it helps.*  Hidden until Emacs answers the page's
  hello that your other devices can reach it (=xwapp-remote-hosts=, and
  an app that can open again), and on a page already on another device.
- *The address only when asked*, as it holds the secret: pressed, the
  button asks Emacs for it, and the page draws the code --- dark on
  white, with the margin a camera needs.  Esc, Close or a click beside
  it puts it away, and so does the phone taking the page.
- The kit's own intents, =xwapp-hello= and =xwapp-qr=, never reach the
  app's handler.  In a browser the hello is the request that makes the
  page the app's; in the xwidget it is the page's first intent, and
  Emacs answers through =XW.kit=.

* Page kit (=ui/=)

What the pages share on the browser side, so it is fixed once:

| File                   | Gives                                                |
|------------------------+------------------------------------------------------|
| =xwapp.js=             | =XW.esc=, =XW.bridge(prefix)=, =XW.sanitizer(opts)=, |
|                        | =XW.browser=, =XW.elsewhere=, =XW.copy(text)=,       |
|                        | =XW.open(url, name)=, =XW.file(name)=; the QR code   |
|                        | for your phone                                       |
| =base.css=             | the shared colours, =box-sizing=, =[hidden]=         |
| =vendor/marked.min.js= | marked 11.2.0 (identical to jsdelivr's)              |
| =vendor/qrcode.js=     | qrcode-generator 1.4.4 (identical to npm's), loaded |
|                        | only when a QR code is shown                         |

A page loads them as =../../xwapp/ui/…=.  That path holds both in the
repo (=local/<pkg>/ui=) and in straight's build (=build/<pkg>/ui=),
because the browser resolves =..= on the URL, not on a symlink's
target; it needs =ui= in xwapp's own =:files=.

- =XW.bridge(prefix)= returns an =emit(op, extra)= that queues intents
  and sets the next title only once Emacs has reset the last, with a
  counter seeded from the clock.  Without the queue, two intents within
  a poll overwrite each other; without the counter, a second identical
  one (a second Refresh) is taken for the one already read.  pr-view
  had neither until it moved here.
- =XW.sanitizer(opts)= returns a =sanitize(html)=: an inert
  =DOMParser= document, a whitelist of tags and attributes, the rest
  unwrapped, links only http(s) and mailto.  Options per page: =images=
  (off by default --- a remote image is fetched just by being shown),
  =classes= (a RegExp per class token; default =language-*=), =attrs=
  and =checks= for page-specific attributes.  clickup-view turns images
  on and adds =data-task= / =data-check=; the herd page takes the
  default.
- Every page also carries a Content-Security-Policy: no inline script or
  handler, no =javascript:= link, no fetch but to ='self'= --- the Emacs
  that served it, in a browser.  The sanitizer is the first
  line; the CSP is what holds if it ever lets something through.  A
  page therefore has no =onerror= / =onclick= attributes of its own.

* HTTP

=xwapp-http= is url.el with the fixes pr-view paid for: 3xx redirects
keep =Authorization= (url.el drops it), =Accept= is not sent twice
(GitHub answers 406), bodies go out as UTF-8 bytes (url.el refuses
multibyte), and =xwapp-parse-json= reads JSON =false= and =null= both
as nil.

=xwapp-http-json= hands parsed JSON to =OK-FN=.  =FAIL-FN= gets
=(CODE ERR BODY URL)= for a failed request, and also for a 2xx it could
not handle (bad JSON, or =OK-FN= signalled) --- then with =ERR= the
condition and =BODY= nil, so a handler bug shows in the page instead of
dying in a url.el timer.

=xwapp-scrub-error= masks any =Authorization= value, Bearer or bare
(ClickUp's =pk_= token).

* Tests

#+begin_src sh
  emacs --batch -L ~/.emacs.d/local/xwapp \
        -l xwapp.el -l xwapp-tests.el \
        -f ert-run-tests-batch-and-exit
#+end_src

The page kit was checked in WebKit (Playwright): the sanitizer's
default and per-page options against hostile markup, and three intents
emitted in one tick all reaching a reader that behaves as xwapp does.
Each page's own harness then ran on the kit, under its CSP.

The browser channel is tested twice.  =xwapp-tests.el= runs the server
and a client speaking HTTP in batch: what is and is not served, a round
trip with non-ASCII text both ways, one page at a time, a closed tab, a
reload; why a page is refused, a soft hello, the address kept and given
back after a restart, and pages opened from a tab.  It was then driven
in Chrome (Playwright, the system Chrome): the same, plus five intents
in one tick arriving in order, a call that throws not stopping the
next, and the three real pages loading under their CSP with no error;
a tab coming back to a second Emacs started after the first was
killed, and to the same Emacs after its requests were held past the
gone (headless Chrome will not freeze a page).  From another device:
the users it serves and the origins it trusts, its fixed port, that the
=Host= serve rewrites to =localhost= is not consulted, and an address
kept over a restart and renewed, in batch; then in WebKit, a page at
=https://= under the box's name, its requests passed on as =tailscale
serve= does --- the =Host= rewritten to =localhost=, the login stamped
--- served, its calls and intents through, another user and no user
refused, and after a restart the open page back and a saved address
working.  The socket is the proof the proxy came through: the
same box request on loopback, dressed in the proxy's headers, is
refused, and =/open/= hands no secret there; the socket and its
directory are yours alone.

** In a browser (=e2e/=)

The pages themselves, in WebKit through Playwright.  The suites that
need Emacs start one in batch (=e2e/apps.el=, =emacs -Q=) serving
pr-view and clickup-view with Bitbucket and ClickUp answered from
=e2e/fixtures/=: nothing reaches the network, no token is read, and a
ClickUp write changes only the fixture's copy of the task.  The browser
reaches that Emacs through a proxy doing what =tailscale serve= does ---
forwarding to the socket, not the loopback port --- so a page opens as
it would on the phone.

#+begin_src sh
  cd ~/.emacs.d/local/xwapp/e2e
  npm ci && npx playwright install webkit   # once
  npm test                                  # or: node run.js narrow cu-edit
#+end_src
