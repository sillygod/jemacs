#+TITLE: ghostherd — design

Why ghostherd is shaped the way it is. The manual is [[file:../readme.org][readme.org]]; this is
the part you read once, or when you are about to change something and
want to know what it was protecting.

Rationale that a *maintainer* needs at the moment of editing lives in
the code as well, not only here. The tmux target rules below, for
instance, are repeated in full in =ghostherd-tmux.el=, because the
person who breaks them will be reading that file and not this one.

* Architecture sketch

#+begin_src text
  UI: overlay (posframe) / side window | consult | modeline | alert | memory
           │
  Control: spawn kill rename prompt message wait handoff | memory search
           │
  Detect:  timer + screen rules + ghostel-exit / OSC hooks
           │
  Host:    capture · screens · send-text · send-keys · live-p
           exited-p · spawn · kill · rename · list · view  ← the slot
           │                              │                    │
  Runtime: ghostel buffer (PTY)      tmux session          Python sidecar
           agent = Emacs child       (PTY, -L ghostherd)   JSON-RPC /jsonrpc
                                                       Qdrant path + FastEmbed
#+end_src

Sessions live in =ghostherd--sessions= (id → =ghostherd-session= struct).
Buffer-local =ghostherd-session-id= links a view buffer back to the
registry — a *view*, since on the tmux backend a session may have none.

Files:

| File                  | Holds                                                 |
|-----------------------+-------------------------------------------------------|
| =ghostherd-backend.el= | session struct, registry, the slot, ghostel implementor |
| =ghostherd-tmux.el=    | tmux implementor, naming, recipe stash, restore       |
| =ghostherd.el=         | everything else — detection, UI, messaging, commands  |
| =ghostherd-memory.el=  | sidecar process + JSON-RPC client (=url.el=)            |
| =server/=              | FastAPI JSON-RPC, importers, Qdrant, FastEmbed          |

** Why a sidecar, and why this sidecar

Emacs does not load FastEmbed or speak Qdrant's protocol.  The options
were: shell out per search (model load on every query); embed Python in
Emacs; or a local process with a small protocol.  ecloud already picked
the third for GCP: FastAPI, JSON-RPC 2.0, =POST /jsonrpc=, =uv run
uvicorn=, Emacs =url.el=, =/health= before a restart.  Memory copies
that contract so there is one way this Emacs talks to a Python helper.

Qdrant is embedded (=QdrantClient(path=...)=), not Dockered.  A second
daemon to remember conversations is more moving parts than the feature
is worth.  Hybrid search is dense cosine plus BM25, fused with RRF, so
an exact identifier like =agy-ghost-commit= still ranks when the
embedding is vague.

The CLI stores stay theirs.  Import distills turns into an index;
it does not rewrite =~/.claude= or =~/.grok=.  Grok recap dumps and
=updates.jsonl= are skipped because they are the same history written
again, and they are most of the bytes.

Two deviations from the Phase 3 plan (see [[file:roadmap.org][roadmap.org]]), both forced:

- The ghostel implementor lives in =ghostherd-backend.el= *with* the
  struct rather than being extracted around it. Splitting them the
  other way is circular: the implementor needs the accessors, and the
  struct is what the whole package is about.
- The tmux server config is *generated* into
  =~/.emacs.d/ghostherd-tmux.conf= from a string, not shipped as a file
  beside the source. A lone =.conf= is not on any package manager's
  default file list, so the shipped version works from a checkout and
  silently does not once built — and a missing config means
  =remain-on-exit off=, which fails a long way from its cause.

* Why tmux, and why not as a multiplexer

Survival is the smaller prize. The larger one is =capture-pane=: state
detection used to scrape the Emacs buffer, which is why so much of Phase
1.1 went into fighting alt-screen behaviour, resize repaints and what
ghostel had or had not rendered yet. capture-pane reads the pane
directly, works when nothing is attached, and does not care how ghostel
draws.

So tmux is here as a *named, detachable PTY that can dump its own
screen*. One ghostherd session = one tmux session on a dedicated socket
(=tmux -L ghostherd=), one window, one pane, =status off=, =prefix
None=. Not windows-as-tabs, not panes-as-layout: either would put a
third navigation layer inside ghostel, and Emacs already multiplexes.
Your own =tmux= on the default socket is untouched.

* Two tmux details worth writing down

- *Targets are =\=NAME:=, always.* Without the =\== tmux prefix-matches,
  so =gh-abc-rev= silently drives =gh-abc-reviewer=. Without the
  trailing colon, the commands that parse a *pane* target — =set-option=,
  =capture-pane=, =send-keys= — resolve a bare =\=NAME= against the
  current session instead. =display-message= is the one that makes this
  worth remembering: given =\=NAME= it prints an empty format rather
  than failing.
- *The config goes on every invocation.* tmux reads =-f= once, in
  whichever process starts the server, and the only ghostherd command
  that can start one is =new-session=. Passing it always puts =status
  off= and =remain-on-exit on= in force *before* the first pane exists —
  a =set-option= after the fact races a CLI that has already drawn its
  TUI at the wrong height. It also means no server lingers between
  herds: tmux exits with its last session, and the next spawn brings it
  back configured.

* What the tmux host costs

Two terminal emulators nested — tmux's VT inside ghostel's — but only
for the agent you are actually looking at.

Resizing an attached agent's window flickers. Dogfooding found this
immediately, and the layer responsible is *not* this one: attaching the
same tmux session from a plain terminal and dragging that window
flickers identically, so it is agy repainting under tmux and nothing
ghostherd can debounce away. Worth knowing before anyone spends an
afternoon on the =jemacs-ghostel-resize-debounce= knob --- which is now
a variable rather than a hardcoded 0.15, since the cost per resize
event really did double and the number should be reachable.

The isolating test costs nothing and is the one to reach for whenever a
symptom could belong to either VT:

#+begin_src bash
  tmux -L ghostherd attach -t '=gh-<hash>-<name>:'
#+end_src

(=prefix None= means no =C-b d=; detach with =tmux -L ghostherd
detach-client= from another shell.)

=ghostel_cmd= does not work inside a tmux-hosted agent: ghostel's shell
integration is installed into the shell *ghostel* spawns, and here it
spawns =tmux attach=. Use =bin/ghostherd= instead, which is what it was
for.

* What a snapshot can and cannot hold

On the ghostel backend, agents are Emacs child processes: when Emacs
exits, they exit. So the most that can be persisted is the *recipe* ---
kind, directory, args, notes --- which is exactly what
=ghostherd-session-recipe= returns. (Phase 3 changed the first sentence,
not the second: on the tmux backend the agent itself survives, and the
same recipe is written onto the host so =ghostherd-restore= can rebuild
the session around a process that never stopped.)

The conversation is not in the recipe, and never can be. But it is not lost
either: it lives in the CLI's own store, and each CLI has a flag to reopen
it. That flag is declared per kind as =:continue-args= in
=ghostherd-agent-specs= rather than hardcoded, so a CLI without one is
representable (=shell= has none) and respawn refuses instead of silently
starting cold.

=ghostherd-respawn= therefore gets most of the way to "my herd came back"
with no new dependency: it frees the old buffer and id, then respawns from
the recipe, appending =:continue-args= when asked. Note *appending* --- a
session spawned with =--model= must come back on that model, not the
default.

Surviving an Emacs quit for real needed a process that is not an Emacs
child --- which is Phase 3, and is what =ghostherd-backend= now selects.
Respawn stays useful either way: after a restart on tmux, restore has
already done the work, so the interesting respawn case is the one it
always was --- a wedged CLI.

* Rule matching case  (was a known issue; fixed)

=:screen-rules= used to match under whatever =case-fold-search= happened
to be when the poll timer fired --- the buffer that was current, in other
words, which no rule author chooses or can even see. The same pattern
could mean two different things on two consecutive ticks.

The bug was never the *value*, it was that there was no value.
=ghostherd--rule-matches-p= now binds it, and binds it to nil, for three
reasons:

1. The patterns were written by reading an agent's screen and copying
   what was on it. Case-sensitive *is* the authored intent; folding was
   an accident of where the timer happened to fire.
2. =ghostherd-output-matches= has always bound it to nil, and one
   package should not match two ways.
3. It is the safer direction under the standing policy of preferring a
   *missed* =blocked= to a false one. Folding made =Running= match the
   word "running" in ordinary agent prose, and =permission= match an
   agent merely discussing permissions --- a false =working= and a false
   =blocked= respectively.

No shipped pattern was rewritten to compensate, which is the part to
watch while dogfooding. Roughly thirty of them contain a cased letter;
the three whose casing the UI might vary are =permission=, =Approve= and
=Allow this=. If one of those starts missing, =ghostherd-explain= shows
it (the pattern will be absent from the match list even though the words
are visible in the tail), and the fix is local and one character wide:

#+begin_src emacs-lisp
  "[Pp]ermission"          ; both, deliberately, rather than by accident
#+end_src

That is the whole reason this waited for a dogfood pass instead of being
a quiet fix: the change had to be *stated* somewhere before it altered
what thirty patterns match.

* Decisions behind the API

The manual states what each entry point does; these are the reasons it
does it that way. Grouped here rather than inline so the manual stays a
manual --- but the load-bearing copy of anything a maintainer needs
*while editing* is the comment in the code, not this.

** Why the session list is an overlay

The list used to be a side window because that is the Emacs-native
overview. It stole 36 columns from every other window, including an
attached agent -- a SIGWINCH and a full TUI repaint -- and it felt like
a dashboard you have to keep open rather than something you summon.

posframe is optional. The overlay is the same buffer and the same keys;
without the library, or on a display that cannot host a child frame,
=ghostherd-sidebar= still opens the side window. Visit, explain, the
log and help dismiss the overlay first: its window is dedicated and its
frame unsplittable, so a =pop-to-buffer= from there has nowhere to go.

Finding a row is not =ghostherd-switch=. The switcher is a jump;
the overlay keeps the table in view, so =/= live-narrows it (flex
on name/kind/state/project/notes) without stealing the completing-read
surface or sending keys through the parent minibuffer. =s= remains a
project pre-filter, AND-ed with the query. Esc clears before it
dismisses, because a non-empty query is something you are still using.

Selecting a row shows a snapshot of that agent's screen under the
table. It is a capture, not an attach -- attaching would SIGWINCH the
agent and steal layout, which is what the overlay exists to avoid.
The last capture rides in =ghostherd--screens= (a hash table, like
reports) so moving between rows is free until a 0.2s debounce
recaptures the one you settled on. =v= turns the pane off.

** Detach is not death

*The one bug this phase had to get right.* The ghostel process in an
attached buffer is =tmux attach=, so its exit means a client went away.
Marking the session =dead= there would fire a notification, make a
handoff give up, and be reverted by the next poll anyway. The exit hook
therefore asks =ghostherd-backend-view-is-host-p= first, and an unknown
backend gets the safe answer.

Showing it is a separate problem, and the answer was wrong once. The
mark rides in the spare character of the two-wide glyph column instead
of getting a column of its own: at the default sidebar width there is no
room for another column, so a =View= column would be fitted away in
exactly the situation that needs it. Marking the detached rows rather
than the attached ones also keeps it silent on the ghostel backend,
where a registered session always has its buffer.

It was originally left out of the sidebar altogether, on the grounds
that the switcher is where you choose an agent. That was wrong, and the
first run of T10 found it: the sidebar is the herd *overview*, and an
overview that cannot distinguish a herd running headless from one you
are watching is not describing the herd.

** Where the recipe lives

On the tmux session as user options, rather than the two obvious
alternatives. Not a sidecar file: that can be deleted while the process
it describes is still running, which is the one thing a recipe must
never outlive. Not the session name: it is not big enough, and =args= is
a list of free text that would need escaping in a field tmux also parses
for =:= and =.=.

=args= is stored as a JSON array for exactly that reason. =notes= is not,
because =call-process= passes a value as one argv entry, so tmux sees
embedded newlines without help.

** Why the agent-shell listing is JSON

Not for tidiness. The previous tab/equals format had no escaping, and
two of the fields are free text: a note containing a tab or a newline
silently turned one record into several, and =reason= holds a raw
=:screen-rules= regexp, which can contain anything at all.

** Answering a menu by number

=ghostherd-answer= presses Up several times before descending. The
highlighted option is not necessarily the first, and counting down from
wherever the cursor happens to be picks the wrong answer.

Arrows rather than the digit because some CLIs accept the number as text
and some only respond to arrows, and there is no way to tell which you
are looking at from outside. Arrows work for both.

** Why agent mail is JSON-RPC on the memory sidecar

tmux-hosted agents cannot use =ghostel_cmd= (the integration is in
ghostel's shell, and here that shell is =tmux attach=).  Putting
=bin/ghostherd= on PATH would work and is what the CLI is for, but
spawn execs the agent directly, so the binary is not there unless
someone configured it.

The sidecar is already a localhost JSON-RPC process Emacs talks to.
=herd_message= / =herd_tick= reuse it: sqlite next to =sources.sqlite=,
not a second daemon.  The sidecar still cannot type into a PTY;
=herd_tick= is Emacs pulling work on the poll it already runs.

Queue-until-idle lives in the sidecar because it has the snapshot.
Pasting into a =working= TUI is how a research dump lands in the
middle of a tool call.  Overlay =m= stays in-process and immediate
on purpose.

=GHOSTHERD_RPC= is injected only after the sidecar has a bound port,
so spawn does not advertise a URL that was never opened.  A restart
that changes port writes =ghostherd-mail/rpc.url=.

** Why handoff is asynchronous

=ghostherd-wait= blocks in a =sit-for= loop, which would freeze you out
of the very editor you are meant to keep working in while the other
agent runs --- and orchestrating without sitting and watching a pane is
the entire point. There is a test that fails if a handoff ever calls
=sit-for=.

Two things it has to get right:

- *Grace window.* An agent does not start the instant it is handed
  something: the CLI has to wake up and print, and until it does the
  screen rules still see the idle prompt from before. Without
  =ghostherd-handoff-grace= the watch would report completion
  immediately, every time.
- *One watch per agent.* A second handoff replaces the watch instead of
  stacking a timer on it, and a callback that throws cancels the watch
  rather than leaving it polling forever.

** What bin/ghostherd had to get right

Two things, both learned the hard way:

- *Quoting.* Every argument is free text --- a prompt can contain quotes,
  backslashes and newlines --- so it is escaped into an Emacs Lisp string
  literal rather than interpolated. Verified by round-tripping through
  the Emacs reader, not by eyeballing.
- *Output goes through a temp file, and the write is pinned to UTF-8.*
  =emacsclient -e= prints the *Lisp representation*, so JSON would come
  back double-escaped as ="[{\"name\":...}]"=. Writing to a file avoids
  that --- but agent output is full of non-ASCII (box drawing, the =❯= in
  a permission prompt), and =write-region= without an explicit coding
  system calls =select-safe-coding-system=, which *prompts*. In batch
  that is an error; in a daemon it blocks forever on a minibuffer nobody
  can answer and wedges the server for every later call too. That is not
  hypothetical: it is what the first version did.

** What the poll path costs

It used to cost one subprocess *per agent* per tick, run synchronously
from the timer. Measured against a real tmux with six shells:

| Shape                                  | Blocks Emacs for | Total  |
|----------------------------------------+------------------+--------|
| Old: 6 =capture-pane= + 1 =list-panes= | 30.5 ms          | 30.5 ms |
| New: one batched fetch, asynchronous   | 6.1 ms           | 10.5 ms |

The blocking column is the one that mattered, and the shape of it more
than the number: =O(N)= forks on a 1.5-second timer, so the cost of
watching an agent was paid again for every other agent in the herd. tmux
takes a list of commands in one invocation --- which
=ghostherd-backend-scroll= already relied on for the wheel --- so the
whole tick is one call: the =list-panes= fields, then a delimiter and a
=capture-pane= per session.

Asynchronous for a different reason than speed. =call-process= does not
come back and cannot be interrupted, so a wedged tmux server did not
stall the *herd*, it stalled *Emacs* --- from a timer, repeatedly, with
the readme already documenting stale servers as a thing that happens.
Now a fetch that has not answered within =ghostherd-tmux-fetch-timeout=
is killed and complained about once, and the herd goes stale instead.

Three things this had to get right, all three confirmed against 3.5a
rather than assumed:

- *A failure abandons the rest of the command list.* One pane killed from
  outside makes its =capture-pane= fail, and every command after it never
  runs. So a partial answer is normal: what came back is used, and any
  session the batch did not answer for is read individually by the
  caller. A marker with nothing after it is reported as *missing* rather
  than as an empty screen, because an empty screen reads as =idle=.
- *stderr must be kept out of the screens.* That abandoned list explains
  itself on stderr (="can't find session: x"=), and a sentence like that
  landing in a captured screen is text the rules would happily match.
- *The delimiter is random per fetch.* The text being delimited is
  whatever an agent chose to print, an agent can print anything, and a
  fixed "unlikely" marker is how this kind of parsing fails months later.

Two consequences worth stating because they look like oversights:

- =ghostherd-tmux-status-ttl= no longer governs the poll path at all. The
  batched fetch asks for the same fields in the same round trip and stamps
  the cache from the answer, which is *why* the sweep runs inside the
  callback rather than before the fetch: ask first, and
  =ghostherd--ensure-sessions= would pay for a second, synchronous
  =list-panes= to learn what the fetch was about to say. A herd
  straddling both hosts still pays that one call per tick, since the
  ghostel group's sweep runs before the tmux answer arrives. A
  single-host herd pays none.
- *No poll backoff, deliberately.* Polling idle sessions less often was
  the obvious fix while the cost was =O(N)= subprocesses; batching
  removed the thing it was fixing. What remains per session is a regexp
  match over forty lines, and a herd is not big enough for that to be
  worth the staleness --- or worth explaining why a =blocked= took four
  seconds to appear.

** An agent knowing its own name

Injected into the environment at spawn, by every implementor, from one
list (=ghostherd-agent-environment=). Not discoverable any other way:
=bin/ghostherd= runs in a shell whose only link to the herd is what it
inherited, and =emacsclient= does not carry the caller's environment into
the form it evaluates --- so an Emacs asked "who is =self=" cannot answer
for that path. The shell substitutes it instead.

The =ghostel_cmd= path *can* answer, and does: it is dispatched inside the
VT parser of the terminal that asked, so the calling session's buffer is
the current one. Two paths, one word, and both had to work before a hook
could say =self=.

On tmux this needs =new-session -e=, which arrived in 3.2. The version is
not parsed --- =tmux -V= says things like =next-3.6= --- and the option is
not probed separately: the spawn *is* the probe, cached, and a failure
retries without identity, which is exactly the herd that existed before
identity did. The alternative considered was exec'ing =env VAR=… agent=
as the command, which needs no tmux feature at all; rejected because a
session spawned with no command (=shell=) then gets nothing, and that is
precisely the session a human types =ghostherd= into by hand.

=GHOSTHERD_SESSION= is fixed at spawn, so a rename leaves a running agent
holding a name the registry no longer has. That is a real edge and it is
documented rather than fixed: tmux can update its session environment,
but not the environment of a process it already exec'd, so the only
honest repairs are a respawn or an alias table --- and an alias table for
old names is a memory leak with a lookup in front of it.

** Why a report is not a mark

=ghostherd-mark-state= already existed, and reusing it for CLI lifecycle
hooks would have been one line. It is the wrong shape: a manual mark is
*sticky*, which is right for a human overriding detection and fatal for a
hook. One missed edge --- a CLI that fires nothing on the way out of a
prompt, a hook chain broken by a config edit --- and the row is frozen at
=blocked= for the rest of the session, notification already sent.

So a report expires, and the pattern it copies is the one already in the
file: OSC progress, down to the freshness check. =ghostherd-report-ttl=
is short (120s) for an asymmetry worth stating plainly:

- when the report was *true*, expiry costs nothing --- the prompt is still
  on the screen, the rules find it, and the herd falls back to the
  behaviour it had before reports existed;
- when the report was *stale*, expiry is the only cure.

A long TTL therefore buys a lie and sells nothing.

Three smaller decisions inside it:

- *Storage is a hash table, not two struct slots.* Adding slots to
  =ghostherd-session= is what "Reloading over a live herd" in
  [[file:../readme.org][readme.org]] is about: every field after the new one shifts under a
  running herd. A report is Emacs-side, transient, and keyed by id ---
  the same shape as =ghostherd--input-at= and =ghostherd--idle-since=,
  and cleared in the same places. Which is also why =ghostherd-rename=
  now moves those three entries to the new id instead of dropping them:
  losing the input grace silently was survivable, losing a report
  mid-prompt is not.
- *A claimed =blocked= loses to a =working= screen.* The rules' =working=
  patterns match a spinner, and an agent emitting tokens is not sitting
  on a prompt whatever its last hook said. =idle= gets no such veto,
  because =idle= is not evidence --- it is what detection falls back to
  when nothing matched. This is the same reasoning as
  =ghostherd-idle-settle=: something appearing on the screen is a
  positive signal, its absence is not.
- *Recording is not deciding.* =ghostherd-report= stores and schedules a
  poll on a zero-delay timer rather than polling in place, because the
  shortest route here is =ghostel_cmd= --- inside ghostel's VT parser,
  where a capture is a subprocess in the middle of drawing a terminal.
  The OSC progress handler is under the same constraint for the same
  reason, and there is a test that fails if this one stops deferring.

The hedges in =ghostherd-poll-session= needed no exemption, which is
worth writing down because it looks like an oversight: both only ever
hold back an =idle=, and the states a hook actually reports --- =working=,
=blocked=, =done= --- pass straight through. Hysteresis exists because
screens lie between two tool calls; a hook firing at the moment the CLI
stops does not need it, and would be ruined by it.

What did need a rule is =done=: it means *finished while you were not
looking*, and the promotion path carried that condition in its own
=if=. A report can say =done= outright, so the rule moved out to where
both paths pass through it.

** What a state reason says

=state-reason= used to hold the =:screen-rules= pattern that matched. That
is a debugging artifact, and it leaked: the desktop notification, the
switcher annotation and =bin/ghostherd state= all showed a regexp where
the agent's question belonged. The readme even had to explain that the
JSON listing needed escaping because "=reason= holds a raw regexp, which
can contain anything at all".

It now holds the *line* the pattern matched, cleaned of the box it was
drawn in --- plus, where one is within =ghostherd-reason-context= rows
above, the nearest line that survives cleaning, joined subject-first:

: Bash(rm -rf build/ && npm publish) — Do you want to proceed?

Subject first because the matched line is usually the *generic* half. On
its own, "needs attention (Do you want to proceed?)" says no more than
"needs attention" did, and it is the specific half that must survive
truncation.

The context lookup is a display heuristic and is allowed to be one: at
worst a notification gains an irrelevant line. It cannot affect *state*,
which is still decided by the pattern alone, and there is a test that
holds that line. Where the matched line cleans away to nothing --- an
anchored prompt like =^>= is all furniture --- the reason keeps the
pattern rather than dressing it with whatever happened to precede it.

** Why the log keeps screens

Rule tuning needs the screen a rule fired against, and =ghostherd-explain=
only offers that while the agent is still sitting on the prompt. Keeping
it in the log means the evidence accumulates whether or not anyone was
watching, which is what turns "tune the rules once there is data" from a
task requiring presence into one requiring only attention.

Only transitions into =blocked= are captured: they are rare --- once per
prompt, not once per poll --- and they are the ones worth arguing about.
Entries and screens are trimmed separately, because 500 one-line entries
cost nothing and twenty 40x120 screens are the actual memory.

** Why the log outlives Emacs

Because the herd does. Phase 3 exists so an agent survives an Emacs quit;
the log's own justification is that "notifications arrive once and are
gone, this is what you read when you get back"; and the most ordinary way
of getting back --- starting Emacs again --- was the one case that threw
it away. Worse, it threw away the *screens*, whose entire argument is that
a rule which fired at 02:00 is unarguable by morning. Overnight is
precisely the span an Emacs restart falls inside.

The mechanism is boring on purpose, and five details in it are not:

- *Appended per entry, not written on the way out.* A
  =kill-emacs-hook= does not run for the crash this is meant to survive.
  One line per transition is cheap enough to pay as it happens, and
  =kill -9= is the test that matters.
- *A plist per line, not the struct.* Printing
  =#s(ghostherd-log-entry …)= reads back into the struct *as it is
  then* --- add a slot and every line written before today returns with
  its fields shifted along, which is the reload trap under "Reloading
  over a live herd" wearing different clothes. A plist tolerates a key
  that did not exist yet and one that no longer does.
- *One line per entry, which needs =print-escape-newlines=.* A captured
  screen is forty lines of box drawing, and without that binding it
  would print as forty lines --- taking the crash-safety property with
  it, since a truncated tail is only harmless while it can be exactly
  one entry. =print-length= and =print-level= are bound for a different
  reason: they are *user* settings, and writing ="..."= into somebody's
  log where their agent's screen should be is a silent corruption.
- *Compacted on read, not on write.* Appending is what keeps logging
  cheap, so the file grows with whatever a session did and both caps are
  applied once, when something is reading anyway. The cost is bounded by
  one session's activity rather than by all of them.
- *One warning, then memory only.* The write happens per state
  transition, so a read-only directory has to cost a single warning
  rather than a message every time an agent changes state.

=ghostherd-log-clear= is the consequence rather than a feature: quitting
Emacs used to empty the log by accident, and something has to do it on
purpose now that nothing does.

** The two OSC integrations that are not hooks

- =ghostel-progress-function= is a single global function, very likely
  someone's spinner. ghostherd saves and *chains to* the previous value,
  and restores it when =ghostherd-mode= is disabled. Its handler runs
  synchronously on ghostel's VT-parser callpath, where slow work stalls
  terminal output, so it only records the report; the poll path decides
  what it means.
- The title is read straight off buffer-local =ghostel--title=. Going
  through =ghostel-buffer-name-function= (ghostel's title→buffer-name
  mapping) would fight ghostherd's own buffer naming.

* Design decisions log

| Decision              | Choice                                      | Why                                      |
|-----------------------+---------------------------------------------+------------------------------------------|
| Lifetime              | Bound to Emacs first, then a host slot      | Simpler first; detach became Phase 3     |
| UI                    | Overlay (posframe) *and* consult            | Summoned overview + fast jump; side window is the fallback |
| Agents                | claude, grok, agy (+ shell)                 | What this machine runs                   |
| Multi-agent           | First-class (pair + message)                | Review / implement split is common       |
| Spawn strategy        | Shell then send CLI line                    | Matches “terminal owns agent”; flexible  |
| State authority       | Screen rules + exit hooks + agent reports   | The CLI knows what a screen only hints   |
| Agent identity        | Injected at spawn, one list per implementor  | Nothing can tell a process afterwards    |
| Reported state        | Expires (TTL), unlike a manual mark         | A missed edge must not freeze a row      |
| Report storage        | Hash table keyed by id, not struct slots    | New slots break a herd across a reload   |
| Poll I/O              | One batched round trip per host, async      | Was O(N) forks, blocking, on a timer     |
| Wedged host           | Give up after a timeout, warn once          | Stale herd beats a frozen Emacs          |
| Poll backoff          | *Not done* --- batching removed the reason   | Staleness with nothing left to buy       |
| Log lifetime          | Appended to a file per entry                 | The restart is the absence it is for      |
| Log on disk           | One plist per line, compacted on read        | Struct slots shift; appending stays cheap |
| Blocked policy        | Strict (miss rather than false positive)    | Same as herdr                            |
| Notify                | Reuse ghostel hooks + alert                 | No parallel notifier                     |
| Kill-on-exit          | Off for herd buffers                        | Keep =dead= rows visible                 |
| Phase 3 host          | tmux as headless PTY, 1 session per agent   | Capture + survive; not a second mux      |
| Backend dispatch      | On a symbol, not a struct subtype           | One session type; the host is a field    |
| Backend default       | =ghostel=, per session at birth             | Switching must not strand a live herd    |
| tmux spawn            | Direct exec, no shell                       | No quoting, no spawn-delay guesswork     |
| tmux recipe           | =@ghostherd-*= session options              | A sidecar file outlives nothing reliably |
| tmux config           | Generated from a string, =-f= every call    | A shipped .conf does not survive a build |
| View vs state         | =buffer= nil means detached, not dead       | Closing a window is not a crash          |
| Shared memory         | Python sidecar, JSON-RPC over HTTP          | Same contract as ecloud; FastEmbed is slow |
| Memory store          | Qdrant local path, not Docker               | One process, no extra daemon             |
| Memory embed          | FastEmbed multilingual MiniLM               | Queries here are 中文 mixed with English |
| Memory import         | Turns from chat, skip grok recap/updates    | Those files are history dumps, not chat  |
| Memory lifetime       | Started on first search/import, not mode    | A model load does not belong on enable   |
| Memory search default | All projects, =C-u= for this one            | The failure is "I forgot which project"  |
| Memory viewer         | Emacs text buffer; list+chunks RPC          | The index is text; no images to render   |
| Memory port           | 49152+, skip occupied, reuse ours           | 8766 collides with local-dev; ecloud is 8765 |
