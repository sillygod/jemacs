Sidecar 的記憶體：從 10 GB 到 1.4 GB

ghostherd 的 sidecar（server/，Emacs 啟動的 Python 服務，負責搜尋 sessions 和 facts）跑幾個小時後，記憶體讀到約 10 GB。這頁記下怎麼量、找到的兩個原因、改了什麼、還要留意什麼，以及沒做的選項。Ask 18e8b5dd，commit d04d3b7。

先說結論

之前看到 ~10 GB 跑了 3 小時 22 分的那個 sidecar
部署前（舊版） 4,331 MB 重啟前那一刻；它每次匯入還會再長
部署後（重啟） 1,428 MB RSS 1.9 GB；herd search 0.22 s
修好了

兩個原因，都不是 ghostherd 自己的程式漏記憶體。會長的那部分是 ONNX Runtime 的記憶體池（arena）：它留住最大那一批嵌入要過的記憶體，不還。起跳就很高的那部分是 embedded Qdrant 的載入方式：一次讀進所有資料，每個向量先變成 512 個 Python float，用完的記憶體還不回系統。關掉 arena、一批改成 16 個 chunk、換一個邊讀邊轉 float32 的載入器之後，sidecar 啟動約 1.45 GB，匯入時穩在 1.8 GB 左右，不再隨匯入變大。硬碟上的資料一個位元組都沒動。

要留意

新的載入器只在 qdrant-client 1.19.x 上啟用。升級後它會自動退回原本的載入方式（記憶體回到多 1.6 GB），要重新量過才放寬。見「取捨與要留意的」。

症狀

10 GB、swap，以及安靜一陣子後的第一次搜尋

活動監視器的「記憶體」欄（也就是 footprint 量的 phys_footprint）讀到約 10 GB。但這 10 GB 大多不在 RAM 裡：部署前那個 sidecar 才跑了 9 分鐘，footprint 就有 4,317 MB，其中只有 2.5 GB 在 RAM，2.0 GB 已經被換到 swap（vmmap --summary）。整台 Mac 的 swap 用了 4 GB 裡的 2.5 GB（sysctl vm.swapusage）。

記憶體一緊，macOS 就把閒著的 sidecar 壓縮或換出去：量的時候它的 RSS 一度掉到約 80 MB，footprint 卻還是 4.3 GB；下次被用到時，RSS 又回到 2.2 GB。所以代價主要不是「RAM 被佔滿」，而是 swap 和壓縮器的空間，以及安靜一陣子後的第一次搜尋：要先把好幾 GB 從 swap 讀回來。這次沒有單獨量第一次搜尋慢了多少，上面這個機制是從 RSS 的起落看出來的。

RSS 和 footprint 不一樣：RSS 是此刻在 RAM 裡的頁，包括映射進來、系統隨時能收回的程式庫；footprint 是這個 process 自己弄髒的記憶體，連被壓縮、被換出去的都算。只有 process 自己釋放，footprint 才會下降，所以要看的是它。

原因一 · 會長的那部分

ONNX Runtime 的 arena 留住最大那一批的記憶體

嵌入模型（sessions 用 bge-small-zh-v1.5，facts 用 paraphrase-multilingual-MiniLM-L12-v2）由 fastembed 透過 ONNX Runtime 在 CPU 上跑。ONNX Runtime 預設開著 CPU memory arena：一個記憶體池，一次推論要多少就向系統要多少，用完不還，留給下一次。一批的工作記憶體隨筆數增加，也隨長度的平方增加。匯入時一批送 256 個 chunk，長的到 512 token，一次就要 2 GB；批次的形狀一變，arena 又要一塊新的。

只載 dense 模型，同一批 256 個長 chunk 跑兩次，footprint 共多了多少（MB）
arena 開，batch 256+5,172
arena 開，batch 32+356
arena 開，batch 8+82
arena 關，batch 256 / 32 / 8+23 / +8 / +22

arena 開、batch 256：第一批後 +3,107 MB，第二批後累計 +5,172 MB。每一種設定下，256 個長 chunk 都花 11.2–12.1 s，一次查詢都是 2 ms。

arena 關掉後不會再「留住」，但一批進行中的峰值還在，所以 batch 也要小：

arena 關，batch一批進行中的峰值 RSS256 個長 chunk
256（原本）+2,024 MB12.0 s
64+742 MB11.7 s
32+547 MB11.6 s
16（現在）+215 MB11.4 s

小批次沒有變慢：CPU 上每個 chunk 的計算量一樣，大批次只是多佔記憶體。

原因二 · 起跳就高的那部分

embedded Qdrant 一次讀進所有資料，每個向量先變成 Python float

Sidecar 用的是 qdrant-client 1.19 的 local 模式（embedded Qdrant）：沒有獨立的 Qdrant 服務，所有 point 都以 Python 物件放在記憶體，存檔時是 storage.sqlite 裡一列一個 pickle。真正留在記憶體裡的資料結構只有 678 MB：

Qdrant 在記憶體裡的東西（85,220 個 chunk）大小
dense 向量：一個 float64 的 numpy 矩陣（85,220 × 512）333 MB
sparse（BM25）向量：每個權重都是 Python 的 int / float 物件，加上 list 和 SparseVector218 MB
payload：文字 38、dict 22、其他值 49109 MB
id 對照、IDF19 MB

但是打開 store 讓 footprint 多了 2.4 GB。差的那 1.7 GB 是載入過程留下的：

  • 它用 fetchall() 一次讀進所有列：約 800 MB 的 pickle 同時在記憶體裡
  • 每個 point 的 dense 向量解開後是 512 個 Python float 的 list：一個 float 物件 24 bytes，加上 list 裡指向它的 8 bytes，一個向量約 16 KB；同樣的向量用 float32 只要 2 KB。全部讀完前它們都留著：tracemalloc 量到 1.4 GB。pymalloc 實際以 32 bytes 一格放一個 float，照這樣算約 1.7 GB，正好對得上差的那部分
  • 最後才把這些 list 疊成一個 float64 矩陣。那些 float 這時才釋放，但它們跟要長留的物件（payload、sparse 向量）交錯放在同一批 1 MB 的 pymalloc arena 裡。一個 arena 只要還有一個活物件就還不回系統，所以這些空間從此留在 process 裡
打開同一個 store，footprint 多了多少（MB）；括號裡是過程中的峰值 RSS
原本的載入器（峰值 3,072）+2,381
同上，PYTHONMALLOC=malloc（峰值 3,131）+2,381
只改成分批讀（峰值 2,623）+2,307
分批讀，每筆向量立刻轉 float32（峰值 955）+783

每一種之後都再叫 macOS 的 malloc_zone_pressure_relief 把空的記憶體還給系統：一個位元組都沒還（0 MB）。換 allocator、光是分批讀都沒用；要讓那些 Python float 根本不堆起來才有用。

改了什麼

三個改動，資料不搬

1 · arena 關掉，一批 16 個

embedder.ARENA = False：每個模型建立時都帶 enable_cpu_mem_arena=False（fastembed 的 TextEmbedding 收這個參數）。embed_batch 從 256 改成 16，GHOSTHERD_MEMORY_EMBED_BATCH 仍可覆蓋。ONNX Runtime 的執行緒照舊限制在兩個（見 sidecar-cpu-embed-burst）。

一批長 chunk 跑完只留下 2 MB，不再是 GB。速度一樣。

2 · 邊讀邊轉 float32 的載入器

store._lean_load() 在 Store 打開 Qdrant 之前，換掉 qdrant_client.local.persistence.CollectionPersistence.load：一次從 SQLite 讀 512 列，每列解開就把 dense 向量轉成 float32 的 numpy 陣列。那 512 個 Python float 立刻就丟了，不會跟長留的物件疊在一起；Qdrant 接著把這些陣列疊成矩陣，矩陣也就是 float32（166 MB，原本 float64 是 333 MB）。

  • 打開 store：+2,381 → +783 MB；峰值 RSS 3,072 → 955 MB；6.9 → 6.1 s
  • 結果一樣：47 個 eval 查詢的 dense 前 30 名，47/47 順序完全相同，分數最多差 7.2e-8；dense 查詢中位數都是 63 ms
  • 只改記憶體裡怎麼放，硬碟上的 pickle 不變。Qdrant 之後寫回一個 point 時，向量照樣是 Python float 的 list
  • 版本護欄：LEAN_LOAD_FOR = ("1.19.",)。其他版本不換，照原本的方式載入，並在 *ghostherd-memory* 留一行：qdrant-client is not one the lean load was made for; loading as it does
  • 測試：tests/test_store.py 用原本的載入器重開同一個 store，比對全部 point 的分數；也測了版本護欄。tests/test_embedder.py 確認每個模型都關了 arena
3 · 小的
  • words.sqlite 加了 PRAGMA journal_size_limit：每次 checkpoint 後 WAL 縮回 8 MB（線上的曾長到 40 MB）。只省硬碟
  • session_eval.py snapshot 也複製 words.sqlite，副本上的 sidecar 不必重建詞索引
線上結果

合併、部署、重啟後：phys_footprint 1,428 MB（重啟前 4,331 MB，更早看過約 10 GB），RSS 1.9 GB，herd search 0.22 s。副本上同一組步驟從 9,035 MB 變成 1,800 MB。

取捨與要留意的

現在的 1.4–1.8 GB 是什麼，什麼會讓它回來

升級 qdrant-client 時

新載入器替換的是 qdrant-client 內部的一個方法，別的版本裡它可能改了樣子，所以護欄只認 1.19.x。升級後 sidecar 照樣能用，只是退回原本的載入方式：啟動時多 1.6 GB，峰值多 2.1 GB。要在副本上照這頁的方法重新量過、跑過測試，確認新版的 load 還是同一回事，再把版本加進 LEAN_LOAD_FOR。

  • facts 的多語模型 0.5 GB：paraphrase-multilingual-MiniLM-L12-v2 的權重，大半是它 25 萬個 token 的詞表嵌入（約 384 MB）。arena 關掉也省不到它；中文 facts 召回靠它（見 cjk-memory-recall）
  • Qdrant 每 1,000 個 chunk 約 10 MB：現在 85k 個約 0.9 GB，store 長大它就跟著長
  • 啟動後第一次匯入 +340 MB，一次：Qdrant 新增 point 時容量不夠，就用 np.resize 把 dense 矩陣放大一倍（_add_point）。之後要等 store 再長一倍才會再發生；之前是 float64，同樣這一步要多一倍
  • 別把 batch 調回去：GHOSTHERD_MEMORY_EMBED_BATCH=256 就算 arena 關著，一批進行中仍會衝到 +2 GB
  • 別把 arena 打開：要改 embedder.ARENA 前，先在副本上跑兩批不同形狀的 batch，看 footprint 會不會一直長
沒做的選項

還能再省多少，為什麼現在不做

  • 把 sessions 搬出 embedded Qdrant

    dense 向量存成 float32 的 .npy 檔、用 mmap 讀（174 MB 乾淨、有檔案在背後的頁，系統要記憶體時直接丟掉就好）；payload 和文字放進 SQLite，跟已經負責 BM25 那一半的 words.sqlite 放在一起。

    再省 約 0.8 GB：1.45 → 0.6–0.7 GB（剩下的大半是 facts 模型）另外 啟動不用再載 6 秒；dense 搜尋估計約 20 ms（沒量過），專案範圍變成一個 mask

    為什麼不做：它要搬資料。Claude Code 已經刪掉的 session，index 裡的就是唯一的一份；搬動就是一次遷移，要有備份、能中斷後接著做、做完逐筆核對，並留著 Qdrant 的檔案以便退回。工作量中到大。這要你決定，不是順手做的事。

    何時再考慮：store 接近約 20 萬個 chunk（現在 85k；照每 1,000 個 10 MB 算，Qdrant 那部分會到 2 GB 左右），或 1.4–1.8 GB 還是嫌大的時候。

  • 閒置時卸下 facts 模型

    省 0.5 GB代價 每個 prompt 都會做 facts 召回，卸下後下一次要多等約 2 秒（估計）載回來

  • 換小一點或量化過的 facts 模型

    省 約 0.35 GB代價 所有 facts 要重新嵌入（便宜，它們都是檔案），中文召回的 eval 要重跑

    可以之後再做。

  • 事先把 dense 矩陣開大，避開第一次匯入的放大

    省 340 MB，只一次代價 再 patch 一處 Qdrant 的內部；不值得

  • Qdrant 服務或 on-disk 模式

    不可行 local 模式不理 on_disk；服務模式要多跑一個服務（沒有 Docker）

  • 換 allocator、叫 malloc 還記憶體

    試過，沒用 PYTHONMALLOC=malloc 一樣 +2,381 MB；malloc_zone_pressure_relief 還了 0 MB

同一天的相關改動

這次是建在它們上面的

  • BM25 那一半有了自己的索引（words.sqlite，server/wordindex.py，ask 880bc57f）：詞的 postings 放在 SQLite，不再在 Python 裡對每個 chunk 計分。BM25 從 0.49 s 到 5.5 ms，herd search 從 0.66–0.9 s 到 0.21–0.25 s；佔 132 MB 硬碟、2 MB 記憶體。當時沒選放在記憶體的 numpy 版本（多 40–80 MB），原因之一就是 sidecar 已經讀到 10 GB
  • gc.freeze()（同一個 ask）：store 載入後把 Qdrant 的 55 萬個物件移出垃圾回收的掃描範圍。原本每次完整回收都要走過它們，186 ms，隨機打在某個請求上；現在 1 ms。新載入器讀進來的物件一樣被凍結
