* Features

- Spawn *claude* / *grok* / *agy* (or a plain shell) as named sessions
- Multiple concurrent agents per project (e.g. implementer + reviewer)
- Session list (=ghostherd-sidebar=): posframe overlay when available, side window otherwise, plus consult switcher (=ghostherd-switch=). Footer shows account usage for claude / grok / agy -- bars fill as you spend, the number is the used percent, and the tooltip spells out used / left / reset (=U= to refresh).
- State polling: =working= / =blocked= / =waiting= / =idle= / =done= / =dead=
- Notifications via =alert= (config uses =osx-notifier=)
- Inter-agent messaging: =ghostherd-message=, =ghostherd-prompt=, =ghostherd-read=, =ghostherd-wait=
- Agents can mail each other through the sidecar (=herd_message= / =herd_list= on =GHOSTHERD_RPC=), without =bin/ghostherd=
- Agents know their own name (=GHOSTHERD_SESSION=) and can say =self=
- Agents can report their own state, so =blocked= / =done= need not be
  scraped off a screen --- see "Agents that report themselves"
- Agents can call herd commands via =ghostel_cmd= (whitelisted; ghostel
  backend only --- see "Hosts")
- Search past claude / grok / agy sessions (=ghostherd-memory-search=) via
  a local Python sidecar (Qdrant + FastEmbed). Complementary: the herd
  is *now*; memory is *before*.
- Shared *curated* memory a project's agents read and write, whatever their
  CLI (=herd remember= / =recall= / =forget=; see "Shared memory"). Distinct
  from the transcript search above: curated facts, not raw transcripts.

* Hosts

An agent has to run *somewhere*, and ghostherd no longer assumes where.
Everything above the host slot — detection, messaging, handoff, the
sidebar — is written against six capabilities, and two implementors
provide them.

| Capability            | =ghostel=                    | =tmux=                        |
|-----------------------+------------------------------+-------------------------------|
| Screen                | buffer text                  | =capture-pane=                |
| Type text / keys      | =ghostel-paste-string= etc.  | =send-keys= / =paste-buffer=  |
| Alive?                | buffer is live               | session is on the socket      |
| Exited?               | process sentinel             | =#{pane_dead}=                |
| Survives Emacs        | no — agent is an Emacs child | yes                           |
| Costs a nested VT     | no                           | only while you are looking    |

#+begin_src emacs-lisp
  (setq ghostherd-backend 'tmux)      ; where new agents start
#+end_src

Only =ghostherd-spawn= reads it. A session keeps the backend it was born
with, so switching does not strand the herd you already have, and
=ghostherd-restore= sweeps *every* backend rather than just the current
one.

Text goes in as one bracketed paste, then Return.  A CLI takes a big
paste in for a moment --- claude folds it into =[Pasted text #2 +20
lines]= --- and a Return inside that moment is lost, so a multi-line or
long paste waits =ghostherd-submit-delay= (0.3s) first.  Then, after
=ghostherd-submit-check-after= (1.5s), ghostherd looks: text still in
the input box of an agent neither working nor on a menu gets Return
again, =ghostherd-submit-retries= (2) times at most, each one in the
herd log with the screen; still there after that, the log says so.
Only the text it sent counts, so it never submits what you were typing.

Why tmux, why one session per agent, and what the nesting costs are in
[[file:docs/design.org][docs/design.org]].

** Attach is optional

Nobody needs to be attached for the herd to work. Detection reads
=capture-pane=; input goes through =send-keys=. =RET= in the sidebar,
=ghostherd-switch= and =ghostherd-visit= are the only things that run
=tmux attach=, inside a ghostel buffer. Killing that buffer detaches;
the agent keeps running.

Both listings say so. The switcher annotates such a session =detached=;
the sidebar appends =ghostherd-detached-glyph= to its state glyph, so a
row reads =○▪= rather than =○=. That is a state of the *view*, not of
=state= --- an agent is working or blocked whether or not anyone is
watching, and detaching never marks it =dead=. See "Detach is not
death" in [[file:docs/design.org][docs/design.org]].

** Surviving Emacs

The recipe — kind, project, command, args, notes — is stashed on the
tmux session itself, as =@ghostherd-*= user options.  =ghostherd-mode=
runs =ghostherd-restore= on enable, so a herd left by a previous Emacs
comes back detached and the first poll fills in its state.

What does not come back is Emacs-side and never could: a manual state
override, whether a session has been seen, the last OSC progress
report. Notes do, because they were written onto the host.

** Sidebar keys

=?= key legend (in the overlay) · =RET= visit · =e= explain · =N= new · =P= pair · =k= kill ·
=r= rename · =R= respawn · =T= relay · =d= its uncommitted changes · =c= note ·
=z= interrupt · =Z= abort ·
=L= herd log · =H= scrollback ·
=a= answer prompt · =m= message · =i= prompt ·
=s= filter by project · =/= live-narrow · =v= preview · =g= refresh · =U= usage · =.= next blocked ·
=M= mark state · =q= / =Esc= quit

=s= opens a project picker in the same pane =?= and =v= use: one row per
project the herd is actually in, with its session count. It starts on the
project of the row under point (or =All projects= when a filter is already
on, so =s RET= still just clears it); =n= / =p= move, =1=-=9= jump straight
to a row, =RET= applies, =Esc= cancels. Every other key is swallowed while
it is open, so =x= cannot kill the session under point by accident.

=/= flex-matches name, kind, state, project, notes and title. Whitespace
is AND (=agy idle=). While typing, =n= / =p= still move; =RET= *applies*
the query and returns to overlay keys, so =j= / =k= move and =RET=
visits the agent. =Esc= clears the query, and closes the list only when
the query is already empty. The project toggle (=s=) is a pre-filter;
both apply together.

The overlay grows a snapshot of the row at point under the table --
=capture-pane= / buffer text, not an attached view. =n= / =p= follow it
after a short debounce. =v= toggles the pane; =ghostherd-sidebar-show-preview=
defaults to on.

When posframe is installed and the display can host a child frame,
=ghostherd-sidebar= opens a centred overlay rather than stealing a
column. =RET= / =e= / =L= / =H= / =?= dismiss it first so the thing they
open does not land in the child frame. Without posframe, or on a tty,
the original side window is what you get. Set
=ghostherd-sidebar-use-posframe= to nil to keep the side window even
when posframe is there.

=?= also prints the glyph legend: =⚠= blocked, =⟳= working, =◷= waiting,
=✓= done, =○= idle, =…= starting, =✖= dead, and a trailing =▪= — in the row's own
colour — for a session with no view attached.

=?= (=ghostherd-sidebar-help=) derives the listing from the buffer's live
keymaps rather than this table, so it stays correct under Evil or any
personal rebinding. Under =evil-collection= the sidebar inherits
=tabulated-list-mode='s *normal* state, where the single-letter keys above
are shadowed; a typical remap moves kill to =x= (so =k= still moves point)
and refresh to =gr= (so the =g= prefix survives). Press =?= to see what is
actually bound.

* Inter-agent communication

Herdr exposes pane/agent primitives over a socket. ghostherd mirrors the
useful subset in Elisp (and via =ghostel_cmd= from inside an agent shell).

** Elisp

#+begin_src emacs-lisp
  ;; Submit work to the reviewer and wait until settled
  (ghostherd-prompt "reviewer" "Review the current diff for security issues" t 180)

  ;; Message with attribution (from implementer → reviewer)
  (ghostherd-message "implementer" "reviewer"
                     "Please review commits on this branch."
                     :submit t)

  ;; Read another agent's recent screen
  (ghostherd-read "reviewer" 80)

  ;; Wait for blocked/idle/done
  (ghostherd-wait "reviewer" '(blocked idle done) 120)
#+end_src

** From an agent shell (ghostel_cmd)

When shell integration is active and the command is whitelisted:

#+begin_src bash
  ghostel_cmd ghostherd-list
  ghostel_cmd ghostherd-state reviewer
  ghostel_cmd ghostherd-prompt reviewer "Review the diff"
  ghostel_cmd ghostherd-message reviewer "Please review" implementer
  ghostel_cmd ghostherd-read reviewer 60
  ghostel_cmd ghostherd-report self blocked "waiting on a decision"
  ghostel_cmd ghostherd-memory-search "posframe overlay"
#+end_src

=self= is the calling agent, and the sender of a =ghostherd-message=
defaults to it: this path is dispatched from the asking terminal, so the
caller is known without being named.

=ghostherd-list= and =ghostherd-state= emit JSON:

#+begin_example
  [{"name":"reviewer","kind":"grok","state":"blocked","reason":"Approve",
    "project":"/src/app/","notes":"reviews auth","age":"3m"}]
#+end_example

An unknown session reports ={"error":...}= rather than a prose string,
so a caller can tell a failure from a session that happens to be named
like one. Why JSON and not the tab/equals format it replaced: see
"Why the agent-shell listing is JSON" in [[file:docs/design.org][docs/design.org]].

Typical workflow:
1. =SPC a h 2= → implementer (claude) | reviewer (claude or grok)
2. Work in implementer
3. =SPC a h m= → message reviewer with a review request
4. =SPC a h .= when reviewer is blocked / done

* Talking to an agent vs operating it

Two different things.

=ghostherd-send= / =ghostherd-prompt= paste *text* and optionally press
Return. That is how you talk *to* an agent, and it assumes the agent is
sitting there waiting for input.

=ghostherd-send-keys= sends *keystrokes*. Escaping a runaway generation,
answering an arrow-driven permission menu, sending EOF --- none of these are
text. Pasting the characters =esc= just feeds the agent a word.

#+begin_src emacs-lisp
  (ghostherd-interrupt "reviewer")          ; Escape -- "esc to interrupt"
  (ghostherd-abort "reviewer")              ; C-c
  (ghostherd-answer "reviewer" 2)           ; pick option 2 of a menu
  (ghostherd-send-keys "reviewer" "tab" "down" "return")
#+end_src

Three things worth knowing:

- Keys do *not* mark the session =working=, though text input does --- the
  usual reason to send a key is to make the agent *stop*. The next poll
  reports what actually happened.
- =ghostherd-answer= is 1-based and drives the menu with arrows, not
  digits, so it works on CLIs that ignore the number.  It counts the
  moves from the choice highlighted on screen --- agy's menu wraps
  around, so Ups "to the top" are not --- and presses Return only once
  the screen shows the highlight on yours; the answer, or why it was
  not given, goes to the herd log.  A menu it cannot read off the
  screen, numbers and highlight, it does not answer.
- Friendly names (=esc=, =C-c=, =down=) are mapped in
  =ghostherd-key-aliases=; each backend translates them into its own
  vocabulary, and anything unlisted is passed through unchanged, so the
  host's full key set stays reachable.

* Waiting

=ghostherd-wait= watches the state machine, which only knows the five states
the screen rules can produce. Plenty of things worth waiting for have no
state of their own --- a test summary, a specific error, the agent naming
the file it just wrote.

#+begin_src emacs-lisp
  (ghostherd-wait "reviewer" '(blocked idle done) 120)   ; by state
  (ghostherd-wait-output "reviewer" "[0-9]+ failures" 300)  ; by output
  (ghostherd-wait-output "reviewer" "deployed" 60 t)     ; nil instead of error
#+end_src

- Returns the matched text; signals on timeout unless NOERROR, so a
  script branching on "did it happen" need not wrap every call in
  =condition-case=.
- Checks *before* sleeping, so output that arrived between the thing you
  triggered and the wait itself is not missed.
- Gives up when the session dies rather than waiting out the timeout.
- Matching is *case-sensitive*, and so are =:screen-rules= --- see
  "Rule matching case" in [[file:docs/design.org][docs/design.org]].

* Mail without the binary

tmux-hosted agents have no =ghostel_cmd=, and =bin/ghostherd= is not on
their PATH.  The sidecar they already share for memory is the bus.

At spawn they get =GHOSTHERD_RPC= (JSON-RPC URL, token included).
=ghostherd-mode= starts the sidecar so that URL exists.  The same URL
is written to =ghostherd-mail/rpc.url= (0600) under
=user-emacs-directory=, with =PROTOCOL.md= next to it.  An agent spawned
before tokens holds a bare URL and gets a 401 that points it at
=rpc.url=; respawning it fixes the environment for good.

#+begin_src bash
  curl -sS "$GHOSTHERD_RPC" -H 'Content-Type: application/json' \
    -d '{"jsonrpc":"2.0","id":1,"method":"herd_list","params":{}}'
#+end_src

=herd_list= (and =herd list= / Telegram's =/herd=) returns sessions in
the same order as the herd page: by state priority (=blocked=,
=working=, =starting=, =waiting=, =done=, =idle=, =dead=) and then most
recently updated (=since= newest first).  =herd_message= queues
={from, to, body, handoff}=.  Each poll Emacs calls =herd_tick=: push
the session snapshot, ack what it already pasted, pull whatever is
deliverable, and periodically prune settled history from =herd.sqlite=
(delivered mail, finished and collected asks, completed commands,
replies and pushes past the retention window, while never touching
open or uncollected rows, active runs, or recent asks still shown by
=herd asks=).  A tick with no answer in
=ghostherd-memory-request-timeout= seconds (60) is given up, and the
next one asks again: url.el now and then drops a request, and the mail
used to stop there.  A target that is =working= is
not deliverable; the sidecar holds the row until it is idle.  Overlay
=m= still pastes immediately and does not use the queue.

A skill lives in =skills/ghostherd-mail/SKILL.md=; copy or symlink it
into the CLI's skill directory.  The herd does not install it for you.

* Telegram bot

The sidecar can long-poll Telegram so a phone can drive the herd
without a public URL --- and tell you, while you are away, what wants
you (below).

#+begin_src bash
  export GHOSTHERD_TELEGRAM_TOKEN=123:abc
  export GHOSTHERD_TELEGRAM_CHAT_IDS=your_chat_id
#+end_src

Then restart the sidecar (=ghostherd-memory-stop= / enable
=ghostherd-mode=, or restart Emacs) so uvicorn inherits the env.

=/herd= lists sessions from the last Emacs poll, ordered by state
priority and recency just like the herd page.  Tap a row for
screen / explain / prompt / interrupt.  =screen= and =explain= reply
from that snapshot immediately (the pane Emacs already captured);
they do not wait for another tick.  A =blocked= session also gets a
button per choice of its menu, in its words (=ghostherd-answer=), and
abort; no number where its menu could not be read, for one picked
blind could be any of its choices.  Kill and respawn sit
behind =more= and a confirm.  Prompt text is queued like herd mail: a
=working= agent does not receive it until idle.

With the herd page on your phone (=xwapp-remote-hosts=), =/herd= also
has /Open the herd page/, and a session's card /Open the room/ ---
its project's room, as its chat --- to open in the phone's browser,
nothing bookmarked: out without the page, ask the bot.  The
addresses hold no secret (below), and Emacs gives them with each
tick; one Telegram would refuse --- not http(s) under a full name ---
is left out, for a button it refuses takes the whole message with it.

Unknown chats are dropped.  The first message from a new chat logs
=telegram ignored chat <id>= in =*ghostherd-memory*= — that id is what
goes in =GHOSTHERD_TELEGRAM_CHAT_IDS=.  Missing token means the bot
task is not started; mail and memory keep working.

** What it tells you while you are away

The herd page shows everything, while you look at it.  The bot pushes
what wants you while you do not (=ghostherd-push=):

| =blocked=      | an agent waits on a menu: what it asks, a button per choice, its screen              |
| =report=       | a lead is done with its turn: its own last message, whole                            |
| =ask-failed=   | an agent's ask failed: whom it asked, why, what it asked                             |
| =used-up=      | an agent stopped with its CLI's usage used up: a button relays it                    |
| =lead-started= | the herd started a lead in a project for a handoff: for whom, the brief's first line |

Each carries Open the room, to the project's room as its chat on the
herd page (=xwapp-remote-hosts=, From your phone above).  Reply to one
and the reply goes to that project's lead, started if it has none.

A push goes only while you look at neither the agent (its buffer, its
room) nor the herd page, here or on the phone, and this Mac has gone
untouched for =ghostherd-push-away-after= seconds (120; it asks
=ioreg=): at the desk the desktop notification is yours.  Nil there
pushes whenever you are not looking.  =M-x ghostherd-push-test= sends
one now, to see that it reaches you.

The room's address in a push holds no secret: Telegram's servers keep
what passes through them.  It asks the page's =/open/ghostherd=, which
Emacs answers only for your Tailscale login, sending the browser on to
the page under its secret.

* Handing work to another agent

=ghostherd-handoff= is the pipeline primitive: message an agent, watch it,
report.

#+begin_src emacs-lisp
  ;; from the implementer, hand a review request to the reviewer
  (ghostherd-handoff "reviewer" "Review the diff on this branch"
                     "implementer")

  ;; with your own completion handler
  (ghostherd-handoff "reviewer" "Run the suite" "user" 300
                     (lambda (session state)
                       (when (eq state 'done)
                         (pop-to-buffer (ghostherd-session-buffer session)))))
#+end_src

*It is asynchronous, deliberately* --- it returns at once and the
callback fires later, so Emacs stays yours while the other agent works.
Two consequences worth relying on: handing off again to the same agent
*replaces* its watch rather than stacking a second one, and for
=ghostherd-handoff-grace= seconds after the handoff a settled state is
not believed, because an agent that has not woken up yet still shows the
prompt it had before.

Why asynchronous, and what the grace window is protecting against:
see "Why handoff is asynchronous" in [[file:docs/design.org][docs/design.org]].

* Asking another agent, and getting the answer back

Mail and handoff go one way.  An ask wants its answer back: the claude
in a project hands a web lookup, a review or a commit to the agy beside
it, and the result arrives as data in the middle of its own task ---
not as a new prompt once it has stopped.

#+begin_src bash
  # from inside an agent the herd started
  "$GHOSTHERD_HERD" ask agy 'Fetch https://... and sum up the API' --wait
#+end_src

=$GHOSTHERD_HERD= is =bin/herd=, a client for the sidecar in Python's
standard library, set at spawn with its absolute name --- tmux-hosted
agents have no =ghostel_cmd=, and a shell profile may rebuild PATH.

- *Who takes it.*  A name, or a kind (=claude=, =grok=, =agy=): that
  kind's agent in the asker's project, a free one first.  Never one in
  another project: an agy elsewhere would commit in the wrong checkout.
- *What the taker sees.*  The work, and the exact command that answers
  it, client path and all.  It needs no skill installed.
- *How it comes back.*  =--wait= prints the answer.  Claude Code should
  run that in the background: it is told when the command exits, and
  the answer is that command's output.  Without =--wait=, the answer
  comes back as mail once the asker is idle --- and so does one a
  waiting asker never collected, because it gave up or died.  A wait
  that loses the sidecar --- Emacs restarting --- waits for it to come
  back, five minutes at most; an answer mailed meanwhile is not
  printed as well.
- *A taker that forgets.*  Stopping without answering closes the ask
  with its screen, marked as such; dying fails it, and so does an ask
  that never left the taker's input box, Return pressed and pressed
  again --- saying so, so the asker hears at once.  A taker that ended
  its turn to wait --- on asks of its own, or work in the background ---
  has not stopped: it is =waiting=, and its ask stays open until a turn
  ends with nothing out.  A real answer sent later still
  replaces the screen or the failure; only a cancel is final.
- *Stopped means its turn ended.*  For a taker whose hooks report, the
  ask closes only on a turn's end its hook says (=Stop=, or grok's
  interrupt) or its transcript does --- claude's marks a turn over
  (=turn_duration=, its final message, the user's interrupt, which
  fires no hook) and one still running, a turn a background task woke
  with no hook saying so --- never on its screen reading idle.  The
  screen is weak evidence: a claude view scrolled back ("Jump to bottom
  (click) ↓") has the spinner out of it and reads idle mid-turn; ask
  18f57d20 was closed that way 23 minutes into one.  Such a view, and
  agy's =/usage= panel, are not read for a state at all: the agent keeps
  the one it had.  A taker with no hooks still settles on its screen.
- *No loops.*  One open ask per agent, a second waits its turn.  An
  agent answering an ask may hand parts of it on --- the lead asks rd,
  rd asks qa --- three asks deep at most, but never to one waiting on
  it.  A kind never picks a project's lead.
- *Rounds.*  While it answers an ask, an agent may ask any one agent
  only so many times: =--rounds N= on the ask it answers, 5 without.
  The next is refused, saying to answer with where it stands.  "rd
  builds, qa tests, four rounds" said to the lead becomes =herd ask rd
  --rounds 4=, and rd's fifth ask of qa never goes out.  An agent nobody
  asked is held to 5 with each agent in one run: from its first ask
  until it finishes a turn with no ask open and no answer on its way.
  You are not held to rounds.
- *Where to see it.*  The Agents tab shows asks on both agents' rows,
  with their round; a project's room says in its header where each run
  stands --- =lead → rd → qa · round 3/4 · waiting on qa=, then
  =done: lead: …= with its report --- and the herd log has each
  delivery and outcome.

Two rules belong in the ask itself (=skills/ghostherd-ask= says them):
a commit names its files, and the asker leaves them alone until the
hash comes back --- the two share a working tree.  And an answer is
data: a fetched page can carry instructions, and the answer is not one.

The taker works under its own approvals; an ask grants nothing.  It can
route /around/ one, though --- an agent kept from pushing can ask one
allowed to --- so the approvals on each agent are the real boundary.

* Relay: an heir takes an agent's name and its work

An agent stops --- its CLI's usage used up, wedged, or you would
rather another CLI went on.  =M-x ghostherd-relay= (=T= in the sidebar,
Relay on the herd page, the button of a =used-up= push) starts a new
agent on the CLI you pick, which takes the old one's name, role, notes
and project: rd the first was claude, rd the second is grok --- =rd II=
in the sidebar and on the herd page, the CLIs of its name on hover.
The old one is killed; its conversation stays where its CLI keeps it,
its id in the heir's line.

The heir's first message is where the work stood.  The sidecar writes
it (=server/relay.py=), because the old one may be past saying
anything:

- *The work* --- the first thing it was asked, then the latest five:
  your prompts, the asks of other agents.  An heir of an heir carries
  the first one's work on, not the brief it was given.
- *Where it got to* --- its last fourteen steps, what it said and ran
  and was answered, its last answer whole.
- *Asks* --- the ones it owed, each with the command that answers it,
  and the ones it waits on.
- *The checkout* --- the branch, what is not committed, the diff's
  stat, the latest commits.

Then what to do with it.  An agent cut short --- working or blocked
when relayed, or its CLI's usage used up --- or owing an ask has work
left: the heir goes on from where it stopped.  One whose turn had
ended was waiting for you: the heir says in two lines where the work
stands, and waits too.

Sixteen thousand characters at most: its oldest steps dropped first,
then its last answer cut --- saying it is the brief that cut it, or an
heir takes it for an answer never finished.  The transcript's path is
in it, for an heir that wants more.

The name is what the rest of the herd knows an agent by, so nothing
else has to change: the lead's asks of rd reach rd's heir, answers to
the asks rd made come to it, and the asks rd was answering are the
heir's to answer --- not failed when rd was killed, nor closed while the
heir sits at its first prompt.  An heir that never comes to its prompt
fails them, saying so.  A lead's heir leads: its role in its flags
where its CLI takes one (claude, grok), in its first message where not
(agy), and it is told again what its project works on.

What the CLI is given: on the same CLI, the old one's own flags (=claude
again= is a fresh conversation, the brief in place of a long or
compacted one); on another, what the project or the CLI's spec gives a
new agent --- one CLI's flags mean nothing to another.

Which CLI: the first of =ghostherd-relay-kinds= (=claude grok agy=)
that is not the agent's own and has usage left, by the usage the herd
reads (=ghostherd-usage-used-up=: under 1% left in a window not yet
reset, read in the last two hours; for agy, by the group the agent's own
model belongs to, so an agent on a group with quota is not called used
up because another is spent).  When an agent stops working with its CLI
used up, the herd says so once for that window --- in the log, the echo
area, a =used-up= push --- and the herd page puts =Relay to grok= first
on its row.

Only the poll decides this.  agy's footer =· AI: Out of credits= is its
paid Google AI credits --- the overage past the model quota, a separate
bucket --- not the quota: a fresh session with the quota full shows that
line and its requests still go through, so it is not read as used up.  No
CLI has a confirmed status string for being out of quota live yet, so the
screen is not read for one.

A lead can relay a stuck or spent worker from the CLI, too: =herd relay
TARGET [KIND] [--reason TEXT]= hands its work to a fresh agent through
the same path, guarded to the lead's own project's agents.

The line of a name is kept with the recipe, so it outlives Emacs on
tmux: the page shows the heir's =II= and, over it, the CLIs before it.

* A lead starts and stops agents (=herd start= / =herd stop=)

A project's lead runs agents through the herd rather than by hand:

#+begin_src sh
herd start KIND [--worktree [BRANCH] | --no-worktree] [--name NAME] [--notes TEXT] [--new]
herd stop NAME
#+end_src

=start= prints the agent's name (and its worktree) for the lead to ask.
It *reuses* an idle agent the lead started whose branch is merged and
worktree clean --- the same agent, with its context, fast-forwarded onto
the main branch --- before spawning a new one; =--new= forces a fresh one.
A worktree is the default once another agent works in the checkout, so two
do not collide; =--no-worktree= runs it in the main checkout.

The herd guards it: only a lead, for its own project (anyone else is
refused); =ghostherd-lead-may-start= (default t) turns the whole thing off;
=ghostherd-lead-start-max= (default 2) caps how many a lead has up per
project; a used-up kind is refused, naming one with quota.  Each agent
carries =started-by= (kept with its recipe, so it survives an Emacs
restart), the log records it, and the card shows "by lead-…".

=stop= kills an agent the caller started --- not one owing an open or
queued ask --- and removes its worktree when merged and clean, else keeps
it.

=herd list= shows a lead what it needs to decide whether to queue work
behind a busy agent or start another: per agent, the open ask and how many
wait behind it, the files its turn is editing, who started it, its worktree
branch, how many commits ahead of its base, and whether it is merged.

* Handoffs: work for another project's lead (=herd handoff=)

An agent in project ghost finds, mid-investigation, that project unnoiac
needs a matching change.  It should neither edit unnoiac's checkout ---
it does not know its rules, and unnoiac's own agents may be at work
there --- nor leave the user to relay it by hand.  It hands it to
unnoiac's lead:

#+begin_src sh
herd handoff PROJECT [TEXT|-] [--wait] [--timeout S] [--rounds N]
#+end_src

=PROJECT= is a path (relative to the shell's own directory), its leaf
name (=unnoiac=, =.emacs.d=) or its store slug, resolved among the
projects the herd knows --- its agents' and its shared-memory stores' ---
to the project's main checkout, so a worktree or a subdirectory names its
project (=server/projects.py=).  It is an *ask* of that project's lead:
=--wait=, =--rounds=, the answer coming back, and the loop rules are an
ask's, across projects as within one --- nobody hands back to whoever
waits on it, three deep at most, and handoffs to a project count as
rounds by the project as well as by its lead.

*Who may send.* Work crosses projects lead to lead, so each lead knows
what happens in its project and nobody from outside directs its agents.
An agent working under its project's lead is refused --- "tell your
lead" --- and puts what the other project needs in its answer to its
lead.  A lead may hand off, and so may an agent in a project with no
lead, an agent in no project, and the user from a shell.  The rule is
about the sender's project, not its role: a herd-wide lead to come,
whose project is the herd itself, routes the user's cross-project
requests through this same handoff unchanged.

The other side of the same rule: an agent's =herd ask NAME= whose taker
is in *another* project is refused, pointing to =herd handoff PROJECT=
--- so cross-project work always goes lead to lead, never straight to an
agent elsewhere.  Asks within a project are unchanged, and the user from
a shell (not an agent) still asks anyone by name.

*The brief.* The herd frames it for the taker: from which project and
agent, that the sender waits on it, and what to do --- plan it in that
project, by its rules, with its agents, and answer with the result.  The
lead's prompt asks the sender for what was found, the evidence (files,
logs, tickets, commits), what is needed, when it is done, and who waits.
Every ask now ends with what to do with work another project needs: a
lead hands it off; any other agent says it in its answer.

*No lead there.* The herd starts one --- the project's own default kind
(=ghostherd-project-kind= in its =.dir-locals.el=) or
=ghostherd-lead-kind= --- and hands it the work; one start however many
handoffs wait on it.  Refused for a directory that does not exist or is
not a git checkout, when =ghostherd-handoff-may-start-lead= is nil, and
past =ghostherd-handoff-lead-max= (3) leads the herd started for
handoffs and still up --- the user decides then.  The new lead's notes
say for whom; the sender did not =herd start= it and cannot stop it.  It
is pushed to your phone (=lead-started=) under the same rules as any
push --- while you are away; at the desk the page shows it.  A lead on a
CLI that takes no role as it starts (agy) reads it after its first ask.

*On the page.* The sender's card: "⇢ waiting on unnoiac (handoff)" ---
"· starting its lead" meanwhile; the taker's: "⇠ ghost is waiting
(handoff)"; the room's run names the taker with its project.  Then the
answer, "⇠ unnoiac answered (handoff)", or why it failed.

* Primary: the herd-wide lead

The user's one entry point for what crosses projects, or where they do
not know which project it belongs to --- and "what is everyone doing?",
"what is stuck?".  One agent, =primary=, that routes and tracks: it hands
work to the projects' leads with =herd handoff= (a project with no lead
gets one), tells the user what came back, and never writes code.

*Where it lives.* The herd's own directory, =ghostherd-primary-directory=
(=~/.ghostherd/primary/=), outside every repo, on
=ghostherd-primary-kind= (claude).  That directory is its project: it has
a memory store of its own, the user's with it as every project has, and
a room.  So the herd's rules hold for it as for any agent, with no
special case --- it may hand off, as an agent in a project with no lead
may; it may not =herd ask= another project's agents (nor their leads:
that is a handoff); and no agent may ask it, which says to tell one's
own lead instead.

*What it does.* =herd list= and =herd asks= across the herd; =herd recall
--project P= on any project; =herd handoff PROJECT= --- a path, or the
name of a project with agents, a memory store, or one claude has run in
(the herd reads =~/.claude/projects= for those).  It writes only its own
memory: a project's is its lead's, the user's the user's.  What is the
user's to decide --- stopping agents, approving a promotion, merging ---
it recommends.  Its role says all this, and how to report: what went
where, who is on it, what to wait for.

*On demand, one conversation.* Started the first time it is written to
--- the page, Telegram, =M-x ghostherd-primary= (with a prefix, a
message too) --- and up until it is stopped.  Stopped, or gone with
Emacs and its host, the next word resumes it on its last conversation:
the one its hooks named, kept beside its directory
(=~/.ghostherd/primary.eld=), on the same CLI.  Nothing of its own runs on
a timer: it wakes when spoken to, or when an answer comes back --- a
handoff's answer is an ask's, back to it.

*Where you reach it.*
- The page: the Agents tab's header opens the Primary room, a chat ---
  there before primary runs; your first message starts it.  Desk and
  phone.
- Telegram: anything you write that is not a command and not a reply to
  a push goes to primary, started or resumed if need be.  A reply to a
  push still goes to that project's lead --- and a reply to primary's own
  report, to primary.
- Emacs: =M-x ghostherd-primary=.

Its report at the end of a turn is pushed while you are away, as a
lead's is (=report=, "↩ Reply to tell primary").

* Shared memory: one memory a project's agents share

A project's agents keep *curated* facts in one place every one of them
reads, whatever its CLI --- "never commit to main", where the retry
scheduler lives, how a thing is deployed.  One fact per Markdown file, in
claude's format (frontmatter name, description, metadata.type) with
provenance (author, created, updated), under
=~/.ghostherd/memory/<slug>/= --- the slug of the project's *main
checkout*, so every worktree shares it --- plus =~/.ghostherd/memory/user/=
for the user's own preferences, shared by *every* project.  This is apart
from =~/.emacs.d/ghostherd-memory= (the raw Qdrant transcripts): that is
*before*, searched; this is the team's *curated* knowledge.

#+begin_src sh
herd remember [--type project|feedback|reference] [--name SLUG] [--user|--project P] [TEXT|-]
herd recall [--user|--project P] [QUERY...]   # no query prints the index; a query, the most relevant facts
herd forget [--user|--project P] NAME
herd promote propose --fact NAME... --file PATH [--project P]   # the exact diff on stdin
#+end_src

The author is =GHOSTHERD_SESSION=, or =user= from a plain shell; the
project is the caller's (a worktree resolves to its main checkout), or the
one its shell is in.  =--project P= reaches any project's store from any
shell --- P a path, a leaf name (=deploy-platform=), or a slug.  The
=MEMORY.md= index is generated by the herd from the files, so concurrent
writers never fight over it and nothing is lost.

Each CLI reaches it its own way.  *claude* writes memory the way it already
does: its =~/.claude/projects/<slug>/memory= is a symlink to the project's
store, made at spawn / worktree / restore (a worktree's points at the main
store).  *grok* and *agy* are told at startup to use =herd
remember/recall/forget= --- grok in =--rules=, agy as a first message.

That opening never drops a fact silently.  The *rules* come first, in full:
the user's facts and the =feedback= ones, which say how to work, not only
what is so.  Then every other fact one line each, =project= before
=reference=, newest first, within =ghostherd-memory-opening-max= (4000
characters, the rules not counted), whole lines only.  Then one line naming
every fact that did not fit, and how to read it (=herd recall <topic>=).
The sidecar composes it from the fact files; without the sidecar the
opening falls back to MEMORY.md's lines under the same cap, with how many
were left out.

=herd recall QUERY= ranks by meaning as well as words, so a query in one
language finds a fact written in another.  The facts are embedded (the same
=bge-small-zh= as the transcripts) into a Qdrant collection of their own,
=ghostherd_facts= --- never mixed with the transcripts --- and kept in sync
with the files however they change: a write, edit or forget through the
herd is indexed at once, and a write that bypasses it (claude writing its
own memory file, a hand edit) is found the next time the store is read, by
the files' stamps, re-embedding only a fact whose text changed.  Until the
embedder is up the ranking falls back to words, and says so.  The page can
call the same ranking (=memory_rank=).

An *ask* carries what memory says about it.  When the herd delivers one,
it appends, under *Relevant memory*, the few facts of the taker's project
most relevant to the ask's text --- at most three, a short excerpt each,
within 1800 characters --- and only when something passes the bar; a grok
or agy taker, which had the rules in full at startup, is not given them
again.  The bar is strict: a fact must stand out from the store by meaning
*and* share words with the same part of the ask (an ask's paragraphs are
weighed apart, since an ask names several things).  Tuned on
deploy-platform's real asks, that found 11 of the 12 facts that clearly
helped and nothing for an unrelated ask.  An ask in Chinese alone, with no
identifier in it, carries nothing.  The ask as stored is what was asked;
only the delivered text grows, and it never waits more than a moment for
it.  Prompts you type yourself are left as they are.

The existing claude memories were migrated in once (=herd memory migrate=,
reversible with =herd memory unmigrate=): each is copied into its store
verbatim, the original backed up (=memory.bak-<date>=, never deleted), and
the claude dir replaced by the symlink.

*Promote a fact into the instructions.*  A memory lives only on this
machine; a stable, general rule belongs in the project's instruction file
(=CLAUDE.md=, or =AGENTS.md= where it links to it), versioned with the code
so every agent and machine sees it --- e.g. "never commit to main".  Which
facts are such rules is an agent's judgment: a lead, or any agent asked, runs
=herd promote propose --fact NAME... --file CLAUDE.md= with the exact diff on
stdin.  The herd *refuses* a fact tied to the machine or the user (a =user=
fact, the user store) and holds the rest pending the *user's* approval, shown
in the Memory tab's *Proposals* section --- the facts, the target file, the
diff, Approve / Reject.  The herd never edits the repo itself: on Approve it
asks the project's lead (or, no lead, the proposer) to apply the diff by the
project's branch/PR rules and reply when done; only then is the fact marked
=promoted: <file> <date>= and does it leave the index, the openings and
retrieval, so it is not loaded twice.  It is reversible (a =Promoted= filter
lists promoted facts, with *Put back in memory*); a reject keeps the fact and
records why.  A *Suggest promotions* button asks the lead to review and
propose.

The *Memory tab* on the herd page shows a project's facts (pick the store, or
it follows the open room), with a filter, the body as Markdown, edit and
delete through the store, and the Proposals / Promoted / Suggest controls
above --- desk and phone.

* Worktrees: two agents in one project at once

An agent can work in its own git worktree, so two agents write code in one
project without stepping on each other.  Opt in when you start one: answer
yes to "Own git worktree" in =M-x ghostherd-new=, or tick *worktree* in the
page's *+ New agent* form.  The herd runs =git worktree add= itself, on a
branch named for the agent off the project's current HEAD, under
=ghostherd-worktree-root= (default =~/.ghostherd/worktrees/<project>/<name>=)
--- outside the project tree, so grep, find and project search in the main
checkout never meet a second copy of the code.

An agent in a worktree still belongs to the project: it shares its room and
its lead, and =ghostherd--project-root= resolves a worktree to its main
checkout (by git's common dir), so an agent started by hand in a worktree
directory is attributed the same way.  Its card shows its branch, how far
it is ahead of its base (=↑N=) and the worktree's size on disk; the size is
measured in the background and cached, not run on every poll.

Dependencies are carried in when the worktree is made, in the background,
by =ghostherd-worktree-deps= (per project, overridable with a
=ghostherd-project-worktree-deps= dir-local): a Python venv is *symlinked*
to the main checkout's (a venv holds absolute paths, so a copy breaks),
=node_modules= is *cloned* copy-on-write (APFS =cp -c=, so the worktree may
diverge it cheaply), and build caches are left off the list.  A dependency
that cannot be cloned is skipped and said so on the card --- never copied in
full.

=herd list= shows each agent's directory and branch, so a lead can find a
worktree agent's work and read it by its branch (=git diff BASE...BRANCH=).

When a worktree agent is killed, the herd removes the worktree and deletes
its branch only if the branch is merged into its base and the tree is
clean; otherwise it keeps both and the project's work line shows it as an
idle worktree.  Removing one is your call: =M-x ghostherd-worktree-forget=
offers the project's idle worktrees and removes the one you pick --- keeping
its branch, so committed work is never lost.  The herd never deletes
unmerged or uncommitted work, and never merges.

Because there is one running Emacs for all worktrees, =bin/reload= refuses a
file that is not under the checkout the live Emacs loads from: reloading a
worktree's copy would overwrite the live definitions with that branch's.

* The guard: an agy agent with no prompts, and no secrets

agy asks before each command it runs, and its own hooks cannot answer
that: an =allow= from a hook does not skip the prompt (agy 1.4.5).  So a
herd agy agent runs with =--dangerously-skip-permissions=, and the herd's
guard is the only gate.  Every tool call goes first to =herd guard=
(=bin/herd_guard.py=, stdlib only), which answers *allow* or *deny* ---
never "ask", which under that flag does not prompt.  A tool it does not
know, a call it cannot read, and the guard failing are all denials.

=ghostherd-agy-guard= (per project in =.dir-locals.el=) picks the rules:

- =auto= (the default) --- reads and writes inside the agent's workspace;
  read-only commands (=grep=, =rg=, =ls=, =cat=, =head=, =find= without
  =-exec= or =-delete=, ...); =git status/diff/log/show/branch/...= and
  the local writes (=add=, =commit=, =switch=, =stash=, =restore=, =mv=),
  which run with git's hooks off; the herd's own commands; and the
  project's own, from =ghostherd-guard-allow-commands= (=("npm test"
  "pytest")=)
- =read-only= --- jnotes' rules: reads and read-only commands only
- =nil= --- no guard; agy prompts as it always has

Everything else is denied with a reason the agent reads.  Some denials are
the user's to lift, *once, for that exact call*: reading outside the
workspace, =git push=, package installs, the network, an unknown command
or tool, and every secret.  Some are never run by an agent, and have no
way through: =rm -rf=, =sudo=, =git push --force=, =git reset --hard=, and
anything touching the guard's own directory.

*Secrets, in layers.*  Where reads are allowed, the agent still never
quietly gets a token or a key:

1. *Not in its environment.*  A guarded agent starts through =herd
   scrub-exec=, which drops every variable matching
   =ghostherd-agent-env-scrub= --- names with a =TOKEN=, =SECRET=, =KEY=,
   =PASSWORD=, =CREDENTIAL=, =AUTH=, ... word, and the =AWS_=, =GH_=,
   =GITHUB_=, =ANTHROPIC_=, =OPENAI_=, =GOOGLE_=, =GEMINI_=,
   =GHOSTHERD_TELEGRAM_= ... families --- keeping
   =ghostherd-agent-env-keep= (=GHOSTHERD_RPC= and the herd's others,
   =SSH_AUTH_SOCK=).  agy logs in from its files in =~/.gemini=, not the
   environment, and runs without them.  What is not there cannot leak
2. *Commands that show the environment or credentials are denied* ---
   =env=, =printenv=, =set=, =export -p=, =declare -p/-x=, any =$VAR=,
   =${...}= or backtick, =ps e=, =launchctl getenv=, =security
   find-*-password=, =gh auth token=, =gcloud auth print-*=, =git
   credential=, =git config credential.*=, an interpreter's inline code
   (=python -c=, =node -e=, =perl -e=, ...), =/proc/*/environ=
3. *Secret files are denied*, to read and to search, inside the workspace
   too: =.env=, =.env.*=, =.envrc=, =*.pem=, =*.key=, =*.p12=,
   =id_rsa*=, =.netrc=, =.npmrc=, =.pypirc=, =.git-credentials=,
   =credentials*=, =*secret*=, =*token*=; =~/.ssh=, =~/.aws=,
   =~/.kube=, =~/.docker=, =~/.config/gh=, =~/.claude=, =~/.gemini=,
   =~/.grok=, the herd's =rpc.token= and =rpc.url=, and git's =.git/config=
   (a remote URL can carry a token).  A symlink is judged by where it
   leads as well as its name, and a file named in an option (=-fFILE=,
   =--from-file=FILE=, =git commit -F FILE=) like any other.  A recursive
   search does not sweep them in passing: the guard rewrites =grep -r= and
   =rg= to leave them and =.git= out (=--exclude=, =--glob '!...'=) and
   =git diff/show/log/grep= to skip them by pathspec, and refuses agy's
   own =grep_search= over a folder that holds one
4. *No redaction after the fact.*  agy's =PostToolUse= cannot change what
   a tool returned --- its payload does not even carry it --- so the first
   three layers hold on their own

*Code outside the guard.*  The layers hold only while everything the agent
runs passes the guard, so the guard also refuses what would run code it
never sees: writing into =.git= (hooks, =core.fsmonitor= in its config)
or the workspace's =.agents=, =.gemini=, =.claude= or =.grok= (agent CLIs'
hooks) asks; git's hooks are off for the agent's own git (a hook is code
it can change --- a tracked =.husky/=, a pre-commit config); =awk -f=,
=awk= that writes (=print > file=), =sort --compress-program=, =rg
--hostname-bin=, =git grep -O=, =--output== are refused.  Two things it
cannot cover, by their nature:

- A project command from =ghostherd-guard-allow-commands= runs code the
  agent can change --- tests, =package.json= scripts --- and so can do
  anything you can, unguarded; only the scrubbed environment holds there.
  Allow only what you would let it run unwatched
- What the agent writes, you may run later yourself (its tests, a hook
  config in the tree, a script): read its diff first

*Approve once.*  A denial the user may lift says so ("they can approve
this exact call once on your card"), and shows on the agent's card and
its room's column, on the desk and the phone: "⛔ needs your approval",
the call, the reason on hover, *Approve once* (also =M-x
ghostherd-guard-approve=).  Approving writes an allowance for that call
--- its tool and arguments, exactly --- into the agent's guard directory,
which the agent cannot read; the herd tells the agent "approved: <call>,
run it again"; the next identical call runs and spends it.  An allowance
unused for 30 minutes lapses.  The herd log has each step: =guard needs
approval=, =approved once=, =ran, approved=.

*Where it runs.*  The guard lives in =~/.ghostherd/guard/<agent>/=
(=ghostherd-guard-root=): its =policy.json=, its =approved.json=, and the
=.agents/hooks.json= agy loads through =--add-dir=, merged with
=~/.gemini/config/hooks.json= (which the herd leaves alone).  agy runs its
tools in its *first* workspace --- that =--add-dir=, not the agent's own
--- so the guard sends every command it allows to where it checked it
(=cd WORKSPACE && ...=, or the call's =Cwd=), and refuses relative file
paths unless agy says it is in the workspace.  The agent's first message
says that a guard decides, names its workspace, and says the guard's
folder is not its own.  The first start of a new agent's guard folder
may ask, on agy's screen, whether to trust it.

A respawn takes the guard as it is then: the flags are worked out at each
start, so turning =ghostherd-agy-guard= on or off reaches an agent the
next time it starts.  grok is not guarded (its =PreToolUse= =ask= prompts
even when always-approving, so it would need its own design).

* From a shell (=bin/ghostherd=)

=ghostel_cmd= reaches the herd from inside an agent's own terminal. This is
for everywhere else --- a Makefile, a git hook, a CI step:

#+begin_src bash
  bin/ghostherd list                       # JSON
  bin/ghostherd state reviewer
  bin/ghostherd prompt reviewer "Run the suite"
  bin/ghostherd handoff reviewer "Review the diff" implementer
  bin/ghostherd keys reviewer down down return
  bin/ghostherd interrupt reviewer
  bin/ghostherd memory search "why was agy-ghost-commit blocked"
  bin/ghostherd memory import
#+end_src

** Which agent am I?

Every agent the herd spawns gets its own name in its environment, on both
backends, because nothing can tell it afterwards:

| Variable            | Holds                                          |
|---------------------+------------------------------------------------|
| =GHOSTHERD_SESSION= | this agent's session name                      |
| =GHOSTHERD_BACKEND= | =ghostel= or =tmux=, informational             |
| =GHOSTHERD_SOCKET=  | the emacsclient socket this herd is running in |

So from inside an agent, everything works without knowing anything:

#+begin_src bash
  ghostherd whoami                            # → reviewer
  ghostherd read self 40
  ghostherd message implementer "found it"    # FROM defaults to reviewer
#+end_src

Any =NAME= may be =self=. =FROM= used to default to ="user"=, which was a
lie whenever an agent was the one talking --- and an agent had no way to
say otherwise.

Two edges worth knowing. =GHOSTHERD_SESSION= is fixed at spawn, so
=ghostherd-rename= leaves a running agent holding its old name; it will
get =unknown session= until it is respawned. And injecting it on the tmux
backend needs =new-session -e=, which is tmux 3.2+: on an older tmux the
spawn still works, with a warning, and agents simply do not know their
own name.

=GHOSTHERD_SOCKET= picks an emacsclient socket; =GHOSTHERD_DRY_RUN= prints
the elisp instead of running it, which is how the quoting is tested.

Arguments may contain anything --- quotes, backslashes, newlines --- and
output comes back as raw UTF-8 rather than a Lisp string. Both took two
attempts; see "What bin/ghostherd had to get right" in
[[file:docs/design.org][docs/design.org]].

* Notifications (ghostel hooks)

ghostherd reuses ghostel's process lifecycle rather than inventing a
parallel notifier:

| Signal                       | Source                        | Herd action            |
|------------------------------+-------------------------------+------------------------|
| View process exit            | =ghostel-exit-functions=      | =dead= *only* if the view is the host |
| Agent exit, tmux backend     | =#{pane_dead}= at poll        | state → =dead= with its status and last words, notify |
| OSC 133 command start/finish | =ghostel-command-*-functions= | shell kind state hints |
| OSC 9;4 progress             | =ghostel-progress-function=   | → =working= (+ %)      |
| OSC 2 title                  | =ghostel--title=              | sidebar Title column   |
| Screen rules (poll)          | timer                         | working/blocked/idle   |
| Desktop notify               | =alert= / =osx-notifier=      | blocked / done / dead  |

Everything in that table except the last two rows needs an attached
ghostel buffer, so on the tmux backend a detached session gets neither
OSC progress nor an OSC 2 title from ghostel. That is fine and was
expected: screen rules carry detection on their own, exactly as they do
when a progress report has gone stale, and the title is still readable
as =#{pane_title}=, which tmux tracks from the same escape sequence.

Neither OSC integration is a hook, and both had to be taken over
carefully --- see "The two OSC integrations that are not hooks" in
[[file:docs/design.org][docs/design.org]].

* Agents that report themselves

Screen rules scrape a TUI that is drawn differently every release, which
is why tuning them is a standing job. But the CLIs already *know* when
they stop for a question and when they finish, and most of them can run a
command at that moment. That command is:

#+begin_src bash
  ghostherd report self blocked "Bash(rm -rf build/) — proceed?"
  ghostherd report self working
  ghostherd report self done
  ghostherd report self auto        # withdraw; back to detection alone
#+end_src

Under tmux that is =bin/ghostherd=; in a ghostel-hosted agent
=ghostel_cmd ghostherd-report self blocked "…"= does the same without
emacsclient. Both need identity, which is why it exists.

claude, grok and agy all run commands from lifecycle hooks, and one
command serves the three: =herd hook= ($GHOSTHERD_HERD, set at spawn).
It reads the hook's JSON on stdin and tells the herd three things ---
the state, the conversation the agent is on, and, when a turn ends,
the answer it ended with.  It goes through the sidecar, so it needs no
emacsclient and no Emacs server.

#+begin_src emacs-lisp
  M-x ghostherd-install-hooks     ; shows the change, then asks
#+end_src

or =herd hooks install= (=status=, =uninstall=, =--dry-run=) from a
shell.  To see what is there first --- every hook each CLI runs, from
user settings, a project's, plugins, grok's own directory and its
Claude/Cursor compatibility --- open the Agents tab: each CLI's usage
card lists them under =hooks=, and a click opens the file at the line.
=herd hooks list= prints the same.  Install adds entries --- never
replaces --- and backs each file up:

| CLI    | Read from                    | Events                                              |
|--------+------------------------------+-----------------------------------------------------|
| claude | =~/.claude/settings.json=    | SessionStart, UserPromptSubmit, Notification, Stop  |
| grok   | the same file (its default)  | the same names                                      |
| agy    | =~/.gemini/config/hooks.json= | PreInvocation, Stop                                 |

The command does nothing in a CLI the herd did not start, so every
session of each CLI can carry it.  A CLI reads its hooks when it
starts: respawn agents to pick them up.

A CLI an agent itself runs --- =claude -p= or =agy -p= from its shell, to
see how another CLI behaves --- inherits the agent's environment, its name
in the herd with it, so its hooks report as the agent: its turns'
=working= and =done=, its conversation, its answer.  The herd drops such a
report whole.  It tells one by the CLI's kind (an =agy= reporting for a
claude agent; a shell session takes any, the CLI run in it being its
agent), and by its process: =herd hook= names the CLI that ran it --- the
nearest process above it that is not a shell --- and the ones above that,
and the herd keeps the agent's own CLI on its link, so a CLI started under
it is not taken for it.  The agent's own CLI on a new conversation
(=/clear=) is followed, and so is a new process not under the old one (a
restart).  Without that, an agent's card followed a probe's conversation
--- or, a probe of another kind, none: a screen dump and no model --- and
read =done= while it worked.

What each event means:

- =UserPromptSubmit=, =PreInvocation= → =working=
- =Notification= of a permission prompt → =blocked=, with its message.
  agy has no such event: its prompts are still the screen rules' job
- =Stop= → =done=, with the turn's last answer --- grok hands it over;
  for claude and agy it is read from the end of the transcript, and
  only when it is past the prompt, so an earlier turn's answer is never
  taken for this one's.  grok's =StopCancelled= withdraws the report
- every event names the conversation, kept by the sidecar, and its
  transcript.  grok's name =updates.jsonl=, its screen's stream of
  updates; the herd reads =chat_history.jsonl= beside it, the
  conversation itself

What the herd does with them:

- a state goes through =ghostherd-report= (below): same TTL, same
  place in the authority order
- an ask its taker finished without answering is closed with that last
  answer, not its screen (see "Asking another agent")
- =ghostherd-respawn= with continue resumes /that/ conversation rather
  than =--continue='s newest one in the directory, which with two agents
  of a kind in one project may be the other's
- the Agents tab shows what each agent last said; =ghostherd-explain=
  shows its conversation; the memory page finds the agent on a
  conversation however it got there

A report is *not* =ghostherd-mark-state=. A manual mark is sticky, which
is right for a human overriding detection and wrong for a hook: one
missed edge and the row is frozen at =blocked= forever. A report expires
after =ghostherd-report-ttl= (120s) instead, the way an OSC progress
report does --- and expiry costs nothing when the report was true, since
a real prompt is still on the screen for the rules to find.

Who wins, in order:

| Authority                        | Beats                                    |
|----------------------------------+------------------------------------------|
| Manual mark (=M= / =mark-state=) | everything, until cleared                |
| Host says the process is gone    | everything below                         |
| A =blocked= rule on the screen   | a report --- a real prompt is never masked |
| A fresh report                   | progress, rules, the idle fallback       |
| A =working= rule on the screen   | a report of =blocked= or =waiting=       |
| OSC progress                     | rules                                    |

The one exception reads oddly and is deliberate: a claimed =blocked=
loses to a screen that positively says =working=, because those patterns
match a spinner --- an agent generating tokens is not sitting on a prompt,
whatever its last hook said. =idle= gets no such veto, because =idle= is
not evidence; it is what detection falls back to.

=waiting= is the one state the sidecar reports for an agent rather than
the agent for itself.  A turn that ends with work it started still out
--- sub-agents, shells, monitors or timers running in the background,
asks of its own open or an answer on its way to it --- ended to wait,
not to stop: its hook says =done=, and the sidecar makes that =waiting
on qa, 2 sub-agents and 1 shell=.  claude, grok and agy all wake an
agent as its background work or sub-agents finish, which is what makes
it a wait.  A background task or sub-agent that was killed or
cancelled is cleared, and one that has gone silent past the staleness
cutoff stops counting: a server left running, or a wait that was
interrupted, will not hold the agent in =waiting= forever.  Its input
box is free, so mail and you reach it and its model can be switched;
but there is no =done= banner, its ask stays open and its run of asks
goes on.  It wakes as that work comes back --- a sub-agent's report
starts a turn of its own --- and the turn that ends with nothing out is
=done=.  It is trusted past =ghostherd-report-ttl=, since the screen
would call it idle, until a =working= screen, a prompt you send or its
next hook says otherwise.  One left waiting with nothing out and no
word from it or its conversation for 30 seconds --- its sub-agents
killed, and it never woke to it --- is =done=.

Reports are for agent kinds. A =shell= session has no agent lifecycle to
report, and a human claiming a state wants =ghostherd-mark-state=.

=ghostherd-explain= shows the current report, its age, and whether it has
expired --- which matters because a report leaves no trace on the screen
below it.

* Why is it in that state? (=ghostherd-explain=)

=e= in the sidebar, or =M-x ghostherd-explain=. Shows the scraped tail, every
=:screen-rules= pattern that matched it, and which one won:

#+begin_example
  agy-review  (agy)

    state    ○ idle
    reason   —
    buffer   *ghostherd:agy-review*

  Matches, in precedence order (blocked > working > idle):

    blocked  ->  Do you want to proceed
    working      Running
    working      esc to interrupt
    idle         ^>

  Only the first line wins.  A rule listed under a
  higher-precedence state shadows every rule below it.
#+end_example

Rule tuning is guesswork without this. A false =blocked= looks exactly like a
real one until you can see *which* pattern matched, and that the agent had
merely printed the words rather than stopped on a prompt.

An exited agent stays visible as =dead= with its last screen until you
kill it from the herd, on either backend --- that is what
=ghostel-kill-buffer-on-exit= nil and tmux's =remain-on-exit on= are for.
Its reason says how it ended and what it said last, =exited 1: No
conversation found to continue= rather than a bare =process exited=: the
last line with a word in it, looked for above the top of the screen too,
where a CLI that clears it on its way out leaves it.  On ghostel's native
PTY the exit status is not passed on, so the reason there is =process
exited: …=.

Screen rules are heuristics against a UI that changes between releases,
so what has been observed against which version is recorded in the
dogfood log in [[file:docs/testing.org][docs/testing.org]]. Prefer a *missed* =blocked= over a
false one.

=working= rules read only the bottom =ghostherd-status-lines= of the
capture (6). These agents scroll, so the tail holds everything the agent
ever printed --- and an agent that writes *about* its own interface puts
every indicator on screen without being busy. It happened twice in a
row: agy quoted =Generating= and =esc to cancel= into a commit summary
about these rules, then claude quoted =esc to interrupt= into an
explanation of that fix. Both sat at =working= until the text scrolled
off.

The bottom six lines are where all three TUIs draw live status --- the
spinner, the input box, and the footer beneath it --- and nothing else.
Both directions cost something, which is why it is a setting: more lines
reads scrollback as status; fewer misses a spinner drawn above a tall
box, survivable only while every kind repeats the hint in the footer
one line from the bottom --- which, below, they do not always.
=blocked= and =idle= still read the whole tail --- a permission box can
be tall, and =idle= is the fallback rather than positive evidence.

agy's rules are additionally anchored to the start of a line, which is
where a TUI draws a status line and prose quoting one does not. claude
is *not*: its hint lives mid-line, in
=⏵⏵ auto mode on … · esc to interrupt · ← for agents=. Same bug, two
kinds, two different discriminators --- which is why the region matters
more than the patterns.

The footer is not always there to lean on.  claude drops
=esc to interrupt= from its footer when the pane is too narrow for it ---
at 52 columns, with a =⧉= item in the footer, it never shows --- and its
spinner's verb is picked at random (=Bloviating…=, =Pontificating…=), so
no word rule catches it either.  Read as idle mid-turn, an agent was
=done= for minutes at a time, twelve times in two weeks.  So a kind may
name its =:spinner=: a pattern for the line it draws above its input box
while it works, by its shape rather than its words ---
=✽ Bloviating… (37s · ↓ 3.3k tokens)=, a glyph, a word, =…=, the time.
It is asked of one line only, the first above the box that is not
indented --- under a spinner sit only indented lines, a tip, a todo
list, the right-aligned update banner --- however far up that is.  Idle,
that line is the first of what the agent last said, which starts at
=⏺=; and past tense, =✻ Baked for 1s=, is not the shape.

grok drops its footer's =Ctrl+c:cancel= while it waits on a task of its
own --- =get_command_or_subagent_output=, a command it sent to the
background --- since there is nothing to cancel then; it read idle for
as long as it waited, twice in a day, two minutes once.  Its spinner
stays, eleven lines up, over its task list and a framed box:
=⠴ Sleep 30s then print probe-done… 0.3s   24s ⇣27.3k [stop]=.  Its
=:spinner= is that shape, braille then its =[stop]= button; what it
said ends at its scrollbar instead.  The lines asked run from the box
up to the first that is not indented, thirty at most: grok indents
everything, claude only what sits under its spinner.

A kind's =working= rules have to cover *every* indicator that CLI shows
while busy. These TUIs draw their input box the whole time, so the
empty-prompt =idle= rule matches during a task too --- precedence is the
only thing keeping them apart, and one missed working signal reports a
generating agent as =idle=. agy cost three of them at once: it labels
its spinner =Generating=, says =esc to cancel= where the others say
=esc to interrupt=, and spins the 8-dot braille family rather than the
6-dot one. Its spinner rule is now the whole braille block ---
enumerating frames is a list of ways to miss one, and nothing else on
these screens draws braille.

* When you get told

=blocked= and =dead= always notify.  =done= is different: it means
*finished while you were not looking*, so it fires only when the agent
was not on your screen at the time --- a window on a visible, focused
frame counts as watched, and being merely displayed does not, since a
frame that is iconified or on another desktop is exactly when a banner
earns its place.

The herd page's room counts too, on the same terms: the page in front
of you on a project's room watches its agents --- each in the columns,
which show its conversation or its screen; in the chat, those whose
conversation is in it.  So a =done= agent with no view of its own, a
detached one, turns =idle= (=seen=) once you have looked at its room,
not only once you have opened it.  The rows of the Agents tab do not
count: a line of what it said is not having read it.

If nothing arrived and you expected it, the herd log says why: a
transition to =idle= rather than =done= means you were watching.

* A turn that ended on a CLI error, and a turn cut short

A turn can die without answering: "Login expired · Please run /login",
or "API Error: … Your computer went to sleep mid-response".  The herd
reads such an error (=ghostherd-cli-errors=, per CLI kind) as =blocked=,
not idle --- so an ask the agent was answering is *held, not closed* with
the error screen, the asker sees the plain reason, and it is answered for
real once the agent can work again.  For an expired login the card, herd
and room, offers a one-click =/login=.

Only the CLI's own error counts, never an agent's words about one.  An
agent that quotes "API Error: Connection lost mid-response" in a reply,
or prints "Login expired" in a test it runs, puts the same characters
at its screen's foot and is not stuck.  claude's transcript tells them
apart: claude writes its own error as an entry of its own
(=isApiErrorMessage=, model =<synthetic>=), and a reply quoting it is the
model's message with no such mark.  So the turn ended on an error only
while that entry is the conversation's last --- what claude writes after
it (the turn's duration, a =/login= run) does not count, and a prompt
typed since starts a new turn.  An error the transcript marks that no
rule names still blocks, with its own words as the reason.  Without a
transcript --- an agent whose hooks have not named one yet --- the screen
decides, and only the last message above the input box counts, when it
begins with the error.

Two of these the herd handles itself: a turn the Mac's sleep cut short,
and a turn a dropped connection cut short ("API Error: Connection lost
mid-response").  The slept error appears only once the machine is awake
again, so a poll seeing it is the wake signal.  The herd waits
=ghostherd-sleep-continue-delay= (45s, for the network to come back), then
sends the agent a prompt --- your turn was cut short, pick up where you
left off --- and the held ask is answered by the continued turn as usual.
The prompt and the card speak of the cause: a dropped connection is
=ghostherd-dropped-continue-prompt=, which says the connection dropped
and never that the computer slept, and the card counts down "continuing
after a dropped connection in /N/s" where a slept turn's says "continuing
after sleep in /N/s", each with a Cancel that leaves it blocked.

It is deliberately timid.  Only these two errors continue ---
=ghostherd-cli-errors= marks them =continue=, ahead of the bare API error,
and nothing else; never a login or any other error (a stalled response, no
network, a 500).  At most =ghostherd-sleep-continue-max= times per stuck
turn (1), whatever cut it: a continued turn that dies again stays blocked,
and the card says the herd stopped retrying ("the connection dropped
again").  It does not fire if, by the end of the delay, you have typed into
the agent, the error is gone, or the session is.  Each continue is in the
herd log, with its cause.

* Scrolling

The agent view scrolls like any other buffer: the wheel, =PageUp= /
=PageDown=, =M-v= / =C-M-v=. Behind tmux the buffer holds one screen and
the history is in the host, so those keys move the *host's* view and the
same buffer shows older output --- you are not sent anywhere else, and
you can keep typing.

The mechanism is tmux copy mode driven by command rather than by a
prefix key, so it never becomes something to learn or get stuck in:
scrolling back to the bottom leaves it automatically. On the ghostel
backend nothing is intercepted, because the buffer already holds
everything and Emacs already scrolls it.

=M->= (or =G= under Evil) returns to the live screen --- which is also
what leaves tmux's copy mode, so it means "put me back where I can
type" rather than being a mode command.

Copying text off the screen is ghostel's copy mode, not tmux's.
=C-z= (the same key as vterm) or =C-c C-t= freeze the current screen so
you can yank; overlay =H= is history.  A full-screen TUI and a tmux
attach both only have one screen, so copy mode is not a way to search
what has scrolled away.

Evil owns those keys in normal state, so it needs its own bindings.
=jemacs-ai= sets both states up:

#+begin_src emacs-lisp
  (evil-define-key 'normal ghostherd-terminal-mode-map
    (kbd "C-y") #'ghostherd-scroll-up
    (kbd "C-e") #'ghostherd-scroll-down
    (kbd "C-u") #'ghostherd-scroll-page-up
    (kbd "C-d") #'ghostherd-scroll-page-down
    (kbd "G")   #'ghostherd-scroll-bottom
    (kbd "C-z") #'ghostherd-copy-mode)

  (evil-define-key 'emacs ghostherd-terminal-mode-map
    (kbd "C-M-v") #'ghostherd-scroll-page-down
    (kbd "M-v") #'ghostherd-scroll-page-up
    (kbd "M->") #'ghostherd-scroll-bottom
    (kbd "C-z") #'ghostherd-copy-mode)
#+end_src

** Reading it elsewhere (=ghostherd-scrollback=)

=H= in the overlay. Dumps the history into an ordinary
read-only buffer instead of moving the live view --- for searching it,
copying out of it, or keeping it open beside the agent.

On the ghostel backend the buffer accumulates everything the agent ever
printed, so scrolling back is just moving point. Behind tmux the buffer
holds only the *visible pane* --- the history is in tmux, where =prefix
None= leaves no way in from the keyboard.

=M-x ghostherd-scrollback= pulls it into an ordinary Emacs buffer, where
every motion you already know works. Putting it back as a tmux key
binding would have made tmux a third navigation layer, which is the one
thing this backend refuses to be.

A full-screen TUI keeps no history at all --- the alternate screen is
never saved --- so for those this shows the current screen, and the
agent's own keys (=ctrl+o=, its pager) are what scroll it.

* What happened while you were away (=ghostherd-log=)

=SPC a h l= opens it as the Log tab of the herd page
(=ghostherd-log-page=); =M-x ghostherd-log= and the overlay's =L= are
the text buffer described below.  The page puts one lane per agent
above the entries: its states as coloured segments across the range
(6h, 24h, 7d, all) --- working blue, waiting teal, blocked orange, idle
grey, done green, dead red --- rebuilt from the transitions, with a count of how
often and how long it sat blocked.  Back from an absence, who was stuck
and since when is one look.  A segment's tooltip has its span and
reason, and a click goes to its entry.  Entries are newest first by
day, filterable by agent, text, or blocked only, and a kept screen
opens in place.  New entries arrive as they are logged
(=ghostherd-log-functions=), and the page needs no sidecar for any of
it.

=SPC a h l=, or =L= in the sidebar. Every state transition and every
prompt sent, oldest first, with a timestamp:

#+begin_example
  22:36:48  reviewer       spawned claude on tmux
  22:36:48  reviewer       starting → working  input sent
  22:36:48  reviewer       ← review the diff on this branch
  22:36:48  reviewer       working → blocked  Bash(rm -rf build/ && npm publish) — Do you want to proceed?  ⏎
  22:36:48  reviewer       blocked → idle  seen
#+end_example

Notifications are the wrong medium for a herd that runs while you are
elsewhere: they arrive once and are gone. This is what you read when you
get back.

A line marked =⏎= kept the *screen* that produced it; =RET= shows it.
Only transitions into =blocked= keep one, and only the last
=ghostherd-log-screens= of them --- which is the other reason the log
exists. =ghostherd-explain= can only answer "why is it in that state"
while the agent is still in it, so a rule that fired at 02:00 would
otherwise be unarguable by morning.

** It survives Emacs, because the herd does

The log is appended to =ghostherd-log-file= as it happens, and read back
when =ghostherd-mode= comes up. So the seam looks like this, and
everything above the middle line is from the Emacs you no longer have:

#+begin_example
  02:14:07  reviewer  working → blocked  Bash(rm -rf build/) — proceed?  ⏎
  09:31:02  herd      resumed 148 entries from an earlier Emacs
  09:31:02  reviewer  restored from tmux, detached
#+end_example

Which closes a hole rather than adding a feature. Phase 3 exists so that
agents outlive Emacs; the log describes itself as what you read when you
get back; and the most ordinary way of getting back was the one that
threw the log away --- including the 02:00 screen, the one case the kept
screens were for.

Appended per entry, not saved on the way out: a =kill-emacs-hook= does
not run for the crash this is meant to survive (verified with =kill -9=).
Caps are applied when the file is *read*, and the file is also compacted
in place on write once its lines or kept screens grow well past
=ghostherd-log-max= / =ghostherd-log-screens=, so a long-lived Emacs
never grows =ghostherd-log.eld= without bound.

=C= in the log buffer forgets the lot, file included --- quitting Emacs
used to do that by accident, and now nothing does. Set
=ghostherd-log-file= to nil to go back to memory only.

* Per-project defaults

Drop this in a project's =.dir-locals.el= and =ghostherd-new= preselects the
kind and prefills the args:

#+begin_src emacs-lisp
  ((nil . ((ghostherd-project-kind . claude)
           (ghostherd-project-args . ("--permission-mode" "acceptEdits")))))
#+end_src

Both are marked =safe-local-variable= for their expected shapes, so no
prompt. They are read *by directory* rather than from the current buffer,
since =ghostherd-new= is usually invoked from the sidebar, which never
picked up the project's dir-locals at all --- and read *before* the kind
prompt, so changing the directory later in the same prompt sequence does
not re-read.

* Shared memory (past sessions)

The herd is *now*. Memory is *before*: search what claude, grok or agy
already did, including in another project, without merging their on-disk
stores.

A Python sidecar (the same shape as ecloud: FastAPI, JSON-RPC 2.0 over
=POST=, =uv run uvicorn=, Emacs =url.el=) imports those transcripts
into a local Qdrant and embeds them with FastEmbed.  It is a persistent
process because the model load is slow; =ghostherd-mode= starts it (so
spawned agents get =GHOSTHERD_RPC=), and so does the first memory
command.  The port starts at *49152* (IANA dynamic/private, well above
ecloud's 8765); if that is taken by something else, the next 31 ports
are tried.  A leftover sidecar in that range is reused when it is on
our token.

It binds loopback, and loopback is not the auth: any web page in a
browser on this machine can POST to =127.0.0.1=.  JSON-RPC is
=POST /jsonrpc/<token>= with =Content-Type: application/json=, the
token in =rpc.token= (0600) under the data directory, created on the
sidecar's first start.  No CORS, and a =Host= other than loopback is
refused.  Why each of those: "Why the sidecar wants a token" in
[[file:docs/design.org][docs/design.org]].

A ghostherd sidecar on a different token --- or from before tokens ---
cannot be used and is not walked past either, since it holds the
Qdrant lock.  One this Emacs started is restarted; any other gets a
message with the command to stop it.

| Store   | What is imported                                      | What is skipped                          |
|---------+-------------------------------------------------------+------------------------------------------|
| claude  | =~/.claude/projects/**/*.jsonl= and =memory/*.md=     | mode / permission / snapshots / images   |
| grok    | =chat_history.jsonl= + =summary.json=                 | recap_requests, updates.jsonl, images    |
| agy     | =brain/<id>/.system_generated/logs/transcript.jsonl= + summaries (fallback: =conversations/*.db= UTF-8 salvage) | internal thinking, sub-agent logs, raw protobuf |

Grok's on-disk bulk is recaps, ACP streams and images, not chat.  Import
does not touch those.  For agy, once a conversation has a
=transcript.jsonl=, any earlier =conversations/<id>.db= source for it is
retired so the index keeps only the clean JSONL turns.

#+begin_src bash
  cd server && uv sync
  # optional, Emacs starts this itself:
  uv run uvicorn main:app --host 127.0.0.1 --port 49152
#+end_src

Then =SPC a h I= (or =M-x ghostherd-memory-import=) once, then =SPC a h /=
to search, or =SPC a h v= to browse the sessions.  Import is CPU-heavy
(FastEmbed) and runs *in the sidecar*, not inside Emacs: watch
=*ghostherd-memory*= for per-file progress; a second =I= while one is
running is a no-op.  Already-imported files are skipped, unless the
importer has since changed how it reads them (below).  =C-u SPC a h
/= starts filtered to the current project; the default is all of them,
because the usual failure is "I forgot which project".

After that first import, the herd keeps the index current by itself:
every five minutes, after a minute of idle, an incremental import runs
in the sidecar (=ghostherd-memory-auto-import-interval=, nil to stop
it).  It is cheap because only chunks that changed are embedded again:
a session being worked in grows by a few turns between imports, and
re-embedding it whole every time would cost tens of seconds of CPU per
active session.  Success goes to =*Messages*= without the echo area; a
failure is said once.
This is not a convenience.  Claude Code deletes a transcript 30 days
after it last changed (=cleanupPeriodDays= in =~/.claude/settings.json=),
and on 2026-10-08 the index here --- imported once, on 2026-08-27 --- held
21 deploy-platform sessions whose files were already gone, while the
ones between that import and the cutoff had vanished unindexed.  It
never runs the first import (that downloads a model and embeds
everything) and never starts the sidecar; a failure tries again within
the hour.  Raising =cleanupPeriodDays= as well keeps the originals.

** The memory page

=SPC a h /= (=ghostherd-memory-page=) and =SPC a h v=
(=ghostherd-memory-sessions=) open a page in an xwidget, built on
=xwapp= like pr-view and clickup-view.  =M-x ghostherd-memory-search=
and =ghostherd-memory-view= are still there, as text, for an Emacs
without xwidgets.

- Search as you type, with agent chips and a project menu (this
  project first).  Hits show the passage around the match, terms
  marked.  Empty, it shows the most recent sessions.
- A hit opens its session *at the hit*: a window of 160 chunks around
  it, Earlier / Later for the rest (49 sessions here have over 400
  chunks, the largest 4617), the hit highlighted, =n= / =N= between
  matches.
- Messages are put back together.  The importer splits a long turn
  into ~1800-character chunks, each starting with the last ~120
  characters of the one before, and records no turn number; the page
  joins a chunk that starts with the previous one's tail, in the same
  role, and drops the repeat.
- What is under /User/ is what you said.  Claude Code writes more than
  your prompts as user turns: every tool's output, the text of a skill
  or command it loaded (=isMeta=), the summary a compaction carries on
  from.  A tool's output is the tool's, and not indexed, as grok's is
  not (=GHOSTHERD_MEMORY_INDEX_TOOLS=1= keeps both); the others are left
  out --- what a summary sums up is in the turns before it.  The room
  shows a compaction as a note.  An importer that reads a transcript
  differently has a new version, and the files it read before are read
  again on the next import, every chunk after the first change embedded
  again: for Claude's version 2, here, about twenty minutes --- 120
  files, 15,283 chunks.
- claude and grok render as markdown, and agy for the turns it imports
  rather than its protobuf =.db= salvage, which stays plain text --- all
  through a whitelist sanitizer with no images: a transcript holds
  whatever an agent ever read.  agy imports clean turns and tool names from =transcript.jsonl=
  (falling back to protobuf UTF-8 salvage only when a session has no
  JSONL log).  Tool calls show as =⚙ Bash= chips.
- Links go to =browse-url=; Copy takes a whole message; Import runs
  without popping the log up beside the page.
- While the sidecar imports --- from this page or in the background ---
  the status line reads its progress every five seconds: agent, files,
  new chunks, the file at hand.
- A session can be picked up again: *Resume* starts a new agent in its
  directory on that conversation (=claude -r=, =grok -r=, =agy
  --conversation=), *Fork* (claude, grok) branches a new conversation
  off it.  The agent is named =<kind>-<project>= with the project's
  default args, and its notes say where it came from.  When an agent is
  already on the conversation, the button opens it instead; a
  transcript written to in the last ten minutes asks first, since it
  may be open in an agent the herd did not start.  When it cannot be
  resumed the page says why --- most often that Claude Code deleted the
  transcript after 30 days and only the index is left.
- The page holds no token and asks the sidecar nothing itself: every
  request goes through Emacs.  For Resume it only names a source; the
  kind, id and directory are the ones Emacs worked out, and an id that
  could read as a flag is refused.
- Keys: =/= search, =↑= / =↓= between results, =RET= open, =Esc= back,
  =n= / =N= matches.

An agent can ask the same index:

#+begin_src bash
  bin/ghostherd memory search "agy-ghost-commit blocked"
  bin/ghostherd memory list
  bin/ghostherd memory view claude-session-id
#+end_src

Data lives in =~/.emacs.d/ghostherd-memory/= (Qdrant path + a sqlite
watermark so a second import only re-embeds what changed).  Prefix
=I= with =C-u= to force a full re-embed.  The default embedding model is
=bge-small-zh-v1.5= (~70 chunk/s on this Mac).  Multilingual MiniLM is
slower and still available via =GHOSTHERD_MEMORY_EMBED_MODEL=.  Not
English-only bge-small-en.  Tests set =GHOSTHERD_MEMORY_FAKE_EMBED=1=
so they never download a model.  Grok tool dumps are skipped (they are
most of grok's bytes and rarely what you search).

Needs =uv= on PATH.  First real embed downloads FastEmbed's model into
its cache; watch =*ghostherd-memory*= if that seems stuck.

  ;; How long after sending input a session is not believed to be idle.
  ;; An agent takes a moment to wake up, and the screen it had before is
  ;; still on show until it does.
  (setq ghostherd-input-grace 6)

  ;; The herd log.  Entries are cheap; the screens kept behind `blocked'
  ;; transitions are the actual memory -- and now the actual disk (about
  ;; 5K each).  Both caps are applied when the file is read, and compacted
  ;; on write when the file grows well past them.
  (setq ghostherd-log-max 500
        ghostherd-log-screens 20
        ;; nil = memory only, and gone with this Emacs
        ghostherd-log-file (locate-user-emacs-file "ghostherd-log.eld"))

  ;; How much screen a state reason carries.  The matched line is usually
  ;; the generic half of a prompt ("Do you want to proceed?"); the subject
  ;; is above it, past however many box-drawing rows the agent drew.
  (setq ghostherd-reason-width 90
        ghostherd-reason-context 3)

  ;; OSC 9;4 progress as evidence of `working'
  (setq ghostherd-use-osc-progress t
        ghostherd-progress-ttl 5)         ; seconds a report stays trusted

  ;; The guard of an agy agent (see "The guard").  Per project in
  ;; .dir-locals.el: ghostherd-agy-guard, ghostherd-guard-allow-commands.
  (setq ghostherd-agy-guard 'auto         ; or read-only, or nil: agy prompts
        ghostherd-guard-allow-commands nil ; ("npm test" "pytest")
        ghostherd-guard-root "~/.ghostherd/guard/")
  ;; ghostherd-agent-env-scrub / ghostherd-agent-env-keep: the variables a
  ;; guarded agent starts without, and those it keeps all the same.

  ;; How long an agent's own report about itself is believed.  Short is
  ;; safe: when the report was true the prompt is still on screen, so
  ;; expiry costs nothing -- and expiry is the only cure for a hook chain
  ;; that broke halfway through a session.
  (setq ghostherd-report-ttl 120)

  ;; OSC 2 title as a sidebar column.  Columns are fitted to the sidebar
  ;; width, and Title outranks Project, so in a narrow sidebar this trades
  ;; the project path for the title rather than overflowing.
  (setq ghostherd-sidebar-show-title nil)

  ;; Host for agents started from now on.  Existing sessions keep the
  ;; backend they were born with.
  (setq ghostherd-backend 'tmux
        ghostherd-tmux-socket "ghostherd"      ; never the default socket
        ghostherd-tmux-default-size '(120 . 40) ; size while detached
        ghostherd-tmux-status-ttl 1.0          ; interactive liveness reads
        ghostherd-tmux-fetch-timeout 10        ; give up on a wedged server
        ghostherd-tmux-config nil)             ; nil = generate one

  ;; Shared transcript memory.  ghostherd-mode starts the sidecar.
  (setq ghostherd-memory-port 49152
        ghostherd-memory-port-tries 32
        ghostherd-memory-search-limit 8
        ;; Background import once the index exists: nil to stop it.
        ghostherd-memory-auto-import-interval 300
        ghostherd-memory-auto-import-idle 60)

  ;; A handoff to a project with no lead starts one there; how many the
  ;; herd may have up that it started so.
  (setq ghostherd-handoff-may-start-lead t
        ghostherd-handoff-lead-max 3)

  ;; Primary, the herd-wide lead: its CLI, and where it works.
  (setq ghostherd-primary-kind 'claude
        ghostherd-primary-directory "~/.ghostherd/primary/")

  ;; Permanent default args example:
  (setf (alist-get 'claude ghostherd-agent-specs)
        (plist-put (alist-get 'claude ghostherd-agent-specs)
                   :args '("--permission-mode" "acceptEdits")))

* Troubleshooting

Symptoms whose cause is a long way from where they show up.

** Reloading over a live herd

Phase 3 added two slots to =ghostherd-session=. Emacs does not migrate
structs that already exist, so a session created before the reload is
read through the new accessors with every field after the new slot
shifted along: =backend= comes back holding a project path.

It is worth knowing what that looks like, because the symptom names
neither the cause nor the cure:

#+begin_example
  Error during redisplay: (eval (ghostherd--mode-line-segment) t) signaled
  (cl-no-applicable-method ghostherd-backend-live-p "/src/app/" #s(ghostherd-session …))
#+end_example

The cure is to clear the registry, which deregisters the sessions and
leaves their buffers and agents alone:

#+begin_src emacs-lisp
  (clrhash ghostherd--sessions)
#+end_src

Do that *before* reloading, not after. Structs cannot be versioned
retroactively, so this could not be repaired --- only named:
=ghostherd--backend-of= now checks that a backend is a symbol and says
the above in one sentence.

Two things were genuinely wrong, though, and are fixed:

- The mode-line segment used to sweep the registry, which was free when
  a host check was =buffer-live-p= and is not once one can run a
  subprocess. Redisplay is no place for I/O, and no place to find out
  that the I/O failed --- a segment that signals breaks the whole
  frame, repeatedly. It now only reads. The poll timer still sweeps.
- =ghostherd--ensure-sessions= treated an unanswerable host check as
  "gone" and pruned. A host is far likelier to be briefly unreachable
  than actually absent, so that deleted the herd instead of reporting
  it. It now keeps what it cannot ask.

** A change to the code took, but a change to a =defcustom= did not

Reloading a file re-evaluates its =defcustom= forms, and =defcustom=
deliberately does *not* overwrite a variable that already has a value ---
otherwise every reload would discard your customizations. So a reload
picks up new *code* and keeps old *defaults*, which is a confusing half
state while the defaults are the thing being edited.

=:screen-rules= live in =ghostherd-agent-specs=, so this bites every
time detection is tuned. It showed up as a rule that plainly should
have matched not matching, with =ghostherd-explain= showing the
now-current code reporting =no rule matched= against a screen the
now-current rules would have caught:

#+begin_src emacs-lisp
  (custom-reevaluate-setting 'ghostherd-agent-specs)
#+end_src

That takes the standard value if you have never customized it, and your
saved value if you have --- so it is safe to run either way, and worth
running after any reload that touched the rules.

** A stale tmux server

A server started without ghostherd's config keeps whatever options it
started with, and =-f= is only read by the process that starts one.
There is no fixing that from Elisp; kill it and let the next spawn
bring it back configured:

#+begin_src bash
  tmux -L ghostherd kill-server
#+end_src

** "tmux has not answered in 10s"

A warning, once, and then a herd whose states stop changing while the
sidebar keeps drawing them. The poll path asks tmux for the whole herd
in one asynchronous call per tick; if that call does not come back within
=ghostherd-tmux-fetch-timeout= it is killed, and the next tick tries
again.

Being told is the whole point. This used to be a synchronous
=call-process= per agent, and =call-process= neither returns nor accepts
=C-g= --- so a server in this state took *Emacs* down rather than the
herd, and looked like Emacs hanging for no reason. What to do about it is
the section above.

** The herd went empty, the agents still running

=tmux -L ghostherd ls= lists them; the sidebar and the herd page do not.
An agent is dropped from the herd only when tmux says its pane is gone
--- no server, or no such session --- and the herd log says so
(=dropped from the herd=).  tmux asked and not answering, a server too
busy to take the connection, is not that: the agents are kept, their
states stale until it answers.  An empty herd is looked for again every
=ghostherd-restore-every= seconds (30), so one emptied all the same
comes back by itself; =M-x ghostherd-restore= brings it back now.  An
agent you were looking at comes back to the buffer still showing it.

The one time this happened for real, tmux was fine: the herd was asked
from a dired buffer whose folder had just been deleted, and Emacs will
not start a process in a directory that is not there.  tmux is started
from your home directory now, whichever buffer is current.

** The agent is drawing into a fraction of the window

Ask the host what size it thinks it is, rather than guessing from what
you can see:

#+begin_src bash
  tmux -L ghostherd display-message -p -t '=gh-<hash>-<name>:' \
       'pane #{pane_width}x#{pane_height} client #{client_width}x#{client_height}'
#+end_src

If the pane is much smaller than the window, the terminal was sized
before it was displayed and never re-synced --- =ghostherd-visit= now
forces a resize after showing the buffer, so revisiting the session
should fix it. Resizing the Emacs window by a column does too, since
that is a real size change and ghostel's own hook fires.

This is easy to mistake for a scrolling problem: the content is there,
the window is big, and only a corner of it is being drawn into.

** Something flickers, or repaints oddly

An attached agent has two terminal emulators between it and you. Before
attributing anything to that, find out which one: attach the same tmux
session from a plain terminal and reproduce it there.

#+begin_src bash
  tmux -L ghostherd attach -t '=gh-<hash>-<name>:'
#+end_src

If it happens there too, ghostel is not involved and neither is
ghostherd. (=prefix None= means no =C-b d=; detach with =tmux -L
ghostherd detach-client= from another shell.) This is not hypothetical
— see "What the tmux host costs" in [[file:docs/design.org][docs/design.org]].

** State is wrong for a CLI

=M-x ghostherd-explain=, or =e= in the sidebar. It shows the scraped
tail, every =:screen-rules= pattern that matched it, and which one won.
A false =blocked= looks exactly like a real one until you can see
*which* pattern matched text the agent had merely printed.

Rules are matched case-sensitively; a pattern that is plainly on screen
but absent from the match list is usually a casing difference. See
"Rule matching case" in [[file:docs/design.org][docs/design.org]].
